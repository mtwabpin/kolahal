* TODO App Functions, so assistants can add and update scripts
Android's App Functions (=androidx.appfunctions=, Android 16 and newer) let an assistant on the
phone call functions an app declares. Kolahal could offer:

- list scripts (name, what it does, on or off), read one script's code;
- add a script, update a script's code;
- run a command script and return what it logged.

Rules, so this stays safe:
- A script an assistant adds or changes arrives switched off, as an imported one does. Switching
  it on shows its access, as today. An assistant can never switch a script on or grant access.
- A changed script shows "Edited" as any edit does, so Compare and Reset to library still work.

** What we found (10 November 2026): possible, but wait
We could build it now; almost nothing could call it yet.

- *It fits*: we already compile and target SDK 37 (the library needs 36+). minSdk 28 can stay:
  the functions only work on Android 16 and newer. We'd add =androidx.appfunctions= and its KSP
  compiler (we don't use KSP yet) and one service class whose functions carry annotations
  (=@AppFunctionServiceEntryPoint=, =@AppFunctionDeclaration=). Its KDoc is what the agent reads.
- *Testing*: =adb shell cmd app_function list-app-functions --package <pkg>= and =… execute …=.
  Google's sample says these commands need Android 17.
- *Who can call it*: only apps holding =EXECUTE_APP_FUNCTIONS=, which is meant for privileged
  system agents. Gemini's support is a private preview for trusted testers; an ordinary assistant
  app from the store can't call it.
- *Still experimental*: Google calls it an experimental preview. The library is alpha or beta
  (sources disagree on the exact version), and the annotations were already renamed once.
- *Early access*: an Early Access Program sign-up form exists (on the overview page). Signing up
  doesn't grant access; Google picks apps.

Next: pick it up when Gemini support opens to all apps, or the library is stable. Cheap steps
before then: sign up for early access; a small prototype (=listScripts=, =addScript=) tested only
through adb, to learn the API.

Sources: https://developer.android.com/ai/appfunctions ,
https://android-developers.googleblog.com/2026/07/build-intelligent-android-apps-appfunctions.html ,
https://developer.android.com/agents/skills/device-ai/appfunctions/skill

** In good shape: keep as it is
- Self-update: checks the package, the version, a higher version code, and that the signers match
  the installed ones and the pinned certificate. The FileProvider covers only =cache/updates/=.
- Script permissions fail closed. =launcher.run= is checked in both processes. Secrets are sealed
  with a Keystore key, filled only for declared https sites, and masked everywhere.
- IPC: every PendingIntent is immutable, =MainActivity= reads no extras, broadcasts between the two
  processes use =setPackage=.
- Backup import parses before it changes anything, uses one transaction per table, strips run
  contexts, drops unknown columns, and imported scripts arrive off.
- The log: SQLite in WAL mode, incremental reload, stable keys; caches are bounded.
- The two-process design overall: shared state goes through =kolahal.db=.
- =Keys= / =Config=: one typed list drives Settings, =config=, completion and backups.
- =tools/check-play-build.sh= runs in CI on every push and checks what Play cares about.
- No =GlobalScope=, no =runBlocking=; singletons hold the application context.
- Commands (decided 13 November 2026): the =when= in =CommandProcessor= stays. Each =CommandSpec=
  holds its other names and whether it is sensitive, and =DispatchNamesTest= checks the =when= labels
  against the catalog, so the guards can't fail open unseen. A map of handlers would cost a day for
  little more.
- Per-command context (cause, batch, capture, =byScript=) stays on thread-locals: no handler is
  =suspend= or starts a script inside =background {}=. A handler that does must pass the context on.
- Tests for command logic (decided 13 November 2026): the logic moves out of the handlers into plain
  functions with JVM tests, as calc, cal, pipes and =commands.off= already were; aliases, typo hints
  and help's catalog checks followed in 0.5.8. No =LogSink= fake and no Robolectric: the device tests
  keep checking the wiring, on the shared =kolahal.db=, one at a time.
