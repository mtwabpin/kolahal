** TODO [#B] Device tests use the old compose rule, which can draw a frame off the main thread  :arch:
- What you'd see: now and then a device test crashes the whole run as a screen closes
  ("Detected multithreaded access to SnapshotStateObserver", then "Must run
  runDetachLifecycle() once…"), and passes when run again. Seen in =HomeScreenTest= (0.5.22's

  after.

  =createAndroidComposeRule=). Move each to the v2 rule. Its =StandardTestDispatcher= runs
  coroutines later than the old one, so a test that expected a change at once needs =waitForIdle()=
  or the test clock. Run each changed class, then the whole suite once.

** TODO App Functions, so assistants can add and update scripts  :project:
Android's App Functions (=androidx.appfunctions=, Android 16 and newer) let an assistant on the
phone call functions an app declares. Kolahal could offer:

- list scripts (name, what it does, on or off), read one script's code;
- add a script, update a script's code;
- run a command script and return what it logged.

Rules, so this stays safe:
- A script an assistant adds or changes arrives switched off, as an imported one does. Switching
  it on shows its access, as today. An assistant can never switch a script on or grant access.
- A changed script shows "Edited" as any edit does, so Compare and Reset to library still work.

*** What we found (10 November 2026): possible, but wait
We could build it now; almost nothing could call it yet.

- *It fits*: we already compile and target SDK 37 (the library needs 36+). minSdk 28 can stay:
  the functions only work on Android 16 and newer. We'd add =androidx.appfunctions= and its KSP
  compiler (we don't use KSP yet) and one service class whose functions carry annotations
  (=@AppFunctionServiceEntryPoint=, =@AppFunctionDeclaration=). Its KDoc is what the agent reads.
- *Testing*: =adb shell cmd app_function list-app-functions --package <pkg>= and =… execute …=.
  Google's sample says these commands need Android 17.
- *Who can call it*: only apps holding =EXECUTE_APP_FUNCTIONS=, which is meant for privileged
  system agents. Gemini's support is a private preview for trusted testers; an ordinary assistant
  app from the store can't call it.
- *Still experimental*: Google calls it an experimental preview. The library is alpha or beta
  (sources disagree on the exact version), and the annotations were already renamed once.
- *Early access*: an Early Access Program sign-up form exists (on the overview page). Signing up
  doesn't grant access; Google picks apps.

Next: pick it up when Gemini support opens to all apps, or the library is stable. Cheap steps
before then: sign up for early access; a small prototype (=listScripts=, =addScript=) tested only
through adb, to learn the API.

** CANCELLED [#C] A companion app for what Play rules out (Kolahal Extras)  :build:project:
- The idea, as Termux does with Termux:API: one Kolahal for everyone (the Play build) and a small
  optional app from GitHub, signed with the same key, holding the accessibility service for =lock=,
  the call log and contacts, which Kolahal would ask through a private interface.
- Built and tried on a phone on 26 November 2026 (it worked), then dropped the same day by the
  maintainer: "This defeats the whole point of extra app, just drop the extra app idea then keep these
  stuff in the full build". The commit and its revert are in the history of the 0.5.19 branch.
- Why: Google Play's rules as read that day. The call log is ruled out by name ("calls appearing in
  … launcher" is a listed invalid use, and an app "may not use alternative methods (including other
  permissions, APIs, or third-party sources)" to get call-log data); contacts through another app are
  not addressed; the lock is probably allowed, but Play Protect blocks an app with an accessibility
  service that is installed from a file in some countries, India among them.
- What stays: the full build keeps the lock, the call log and contacts; the Play build has none of
  them. A launcher may declare an accessibility service on Play itself, with a declaration and a
  disclosure: that is the other way to the lock, not looked into.

** WAITING [#C] Rich responses from scripts with A2UI  :scripts:project:
- A2UI is Google's open protocol with which an AI agent describes a UI as data, and the app draws it with its
  own components. Watched, not planned (the maintainer, 22 November 2026).
- The idea: a script that asks an AI service may hand its A2UI answer to Kolahal, which draws a small, safe part
  of it as a card in the log or a widget, with the components scripts' cards already have. TTY could follow.
- Why it waits: the protocol's 1.0 came out on 11 November 2026, but Android's renderer
  (=androidx.a2ui.compose=) is at 1.0.0-alpha02 and supports 0.9.1. Look again when it supports 1.0.
- To settle then: a button in an answer must not run a command unasked, and what is sent to the service is the
  script's and the user's choice.
- Looked at again on 27 November 2026 (progress and what people who used it report): a model that
  writes A2UI directly spends many times the tokens of plain text or of a small format of the app's
  own, and the fix for that (A2UI Express) exists only in server SDKs. No model is tuned for it,
  and everyone validates, retries and falls back to text.
- Remark: decided 27 November 2026. The Assistant's Rich answers stay as built, an optional switch;
  nothing more is built on A2UI (no own catalog or theming, no A2UI from scripts), because of the
  token cost. Only what a new library version forces is done.

* Keep as it is
Checked and found sound, or left as it is on purpose. Don't raise these again.

- Self-update: checks the package, the version, a higher version code, and that the signers match
  the installed ones and the pinned certificate. The FileProvider covers only =cache/updates/=.
- Script permissions fail closed. =launcher.run= is checked in both processes. Secrets are sealed
  with a Keystore key, filled only for declared https sites, and masked everywhere.
- IPC: every PendingIntent is immutable, =MainActivity= reads no extras, broadcasts between the two
  processes use =setPackage=.
- Backup import parses before it changes anything, uses one transaction per table, strips run
  contexts, drops unknown columns, and imported scripts arrive off.
- The log: SQLite in WAL mode, incremental reload, stable keys; caches are bounded.
- The database's sync mode: with write-ahead logging Android uses NORMAL, so a log line doesn't
  wait for the disk. Read from =dumpsys dbinfo= on a phone and on the emulator, both Android 16, on
  23 November 2026. Older versions were not checked.
- The two-process design overall: shared state goes through =kolahal.db=.
- =Keys= / =Config=: one typed list drives Settings, =config=, completion and backups.
- Theme files are read by a regex on purpose: it also reads a hand-edited file.
- =tools/check-play-build.sh= runs in CI on every push and checks what Play cares about. Checked 22
  November 2026: the build workflow skips a push that changes only docs, the site, =.md= or =.org=
  files; the release workflow runs it too.
- No =GlobalScope=, no =runBlocking=; singletons hold the application context. Checked 22 November
  2026: no =GlobalScope=, but one =runBlocking=: =ui/editor/TextEditorViewModel.kt= (=onHidden=) waits up to
  2 seconds for the text editor's draft to be written as its window leaves the screen.
- Commands (decided 13 November 2026): the =when= in =CommandProcessor= stays
  (=terminal/commands/CommandProcessor.kt=, =execute=; the bodies of its built-in commands are in
  command groups such as =SystemCommands= and =LogCommands=). Each =CommandSpec= holds its other
  names (=aka=) and whether it is sensitive, and =DispatchNamesTest= (in =ReservedNamesTest.kt=)
  checks the =when= labels against the catalog, so the guards can't fail open unseen. A map of
  handlers would cost a day for little more.
- Per-command context (cause, batch, capture, =byScript=) stays on thread-locals: no handler is
  =suspend= or starts a script inside =background {}=. A handler that does must pass the context on.
- Tests for command logic (decided 13 November 2026): the logic moves out of the handlers into plain
  functions with JVM tests, as calc, cal, pipes and =commands.off= already were; aliases, typo hints
  and help's catalog checks followed in 0.5.8. No =LogSink= fake and no Robolectric: the device tests
  keep checking the wiring, on the shared =kolahal.db=, one at a time.
- Data migrations (=Keys.migrate=, =Db.upgrade=, the =OLD_*= stores, the "before 0.4.2" log paths)
  and =ScriptScheduler='s old =dailyTag= cancel: old installs may still need them.
- The three "needs usage access" messages are the same call; the duration formats differ on
  purpose; the Lua and JS functions are already checked against each other by =ApiDocsTest=.
- =WidgetWords.agenda= handles a script's own agenda, so it isn't a copy of =Agenda.group=.
- The three layers are enforced (LayersTest), and every preferences file and key-value scope is
  declared once, with its backup rules (=data/Stores.kt=, StoresTest).
- Pure logic is already pulled out and JVM-tested in many places (WidgetWords, SelectorMath,
  EditorLogic, =mergePage=, InstantRun), across 193 unit-test files.
- Script runs are well contained: a separate process, a lock for each script, limits in HostApi,
  and careful threading in the view model.
- State is always shown: the empty log says what to type, Undo follows a delete, the
  scroll-to-bottom chip has a full 48 dp target, and cards say "Allow calendar access" with the tap
  that asks for it.
- Gestures are guarded with care: the double-tap detector is added only when it is set, swipe up
  is off by default, the pinch takes only two-finger touches, and the full seek bar keeps its drag
  from the pager.
- The layout stays still under a finger: each pinned item has one height, the prompt keeps its
  height when the keyboard opens, and suggestions can't push it off the screen.
- Screens keep their filters, search and scroll while the editor or another screen is in front, and
  the editor saves on Back and when the app stops.
- Destructive actions on scripts and feeds ask first and name what is lost; Update, Reset and
  removing a source offer Undo.
- Empty, loading and error states are written out nearly everywhere, with the next step beside them.
