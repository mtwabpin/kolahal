#+TITLE: Working on Kolahal
#+STARTUP: showall

A quick reference for changing the code: building, how the parts fit, where things are, and the
usual changes. [[file:codebase-guide.org][codebase-guide.org]] is the long, guided tour; [[file:release/README.org][release/]] covers signing and
publishing.

* Build

#+begin_src sh
./gradlew :app:assembleDebug              # debug APK ("Kolahal debug", package suffix .debug)
./gradlew :app:assembleRelease            # R8-optimized; signed with keystore.properties or the debug key
./gradlew :app:bundlePlay                 # Google Play: release without accessibility, the call log, reading contacts and update
./gradlew -PplayApk :app:assemblePlay     # the same as an APK, signed with the release key (GitHub releases)
./gradlew :app:testDebugUnitTest          # JVM tests
./gradlew :app:connectedDebugAndroidTest  # on-device: engines, sandbox, :script process, commands, screens
tools/device-tests.sh                     # the same on one or two emulators, each running half
#+end_src

The on-device tests install the debug build and change its settings: run them on an emulator, never
on a phone you use.

- Toolchain :: AGP 9.5.2, Gradle 9.9.1, Kotlin 2.4.21, compileSdk 37.1, targetSdk 37, minSdk 28,
  Jetpack Compose (BOM 2026.11.01), Java 17 bytecode. Material 3 is set apart from the BOM, at
  =1.5.0= (=material3= in =gradle/libs.versions.toml=), for the Expressive components.
  The NDK is pinned (=ndkVersion=, 28.2.13676358, AGP's default): it strips the native libraries
  (Lua, QuickJS) and keeps their symbols in the Play bundle; the workflows install the same one.
- Baseline profile :: =app/src/release/generated/baselineProfiles/= (the baseline profile and a
  startup profile; the Play build uses the same) is generated by the =:baselineprofile= module
  (cold start with notification access on, typing, help/apps output, log scroll, settings, the
  Shaders tab, the script editor, the app selector on the edge, the widgets page). Regenerate with
  only an emulator attached (it reinstalls the app and drives every connected device):
  =./gradlew :app:generateReleaseBaselineProfile=.
- Signing :: =keystore.properties= (git-ignored) names the release key, which signs the APKs
  (=storeFile=, =storePassword=, =keyAlias=, =keyPassword=), and the upload key, which signs the Play
  bundle (=uploadStoreFile=, =uploadStorePassword=, =uploadKeyAlias=, =uploadKeyPassword=); the
  =KOLAHAL_RELEASE_*= and =KOLAHAL_UPLOAD_*= environment variables do the same in CI.
  =tools/make-keys.sh= makes both keys and the file; =tools/make-keys.sh --secrets= stores them for
  GitHub Actions. Without a release key the APK is signed with the debug key; without an upload
  key the bundle stays unsigned. Why there are two keys, and the whole release setup:
  =docs/release/README.org=.
- GitHub Actions :: =build.yml= runs the unit tests, builds both and runs the Play check on every
  push that changes the app (once per commit) and on pull requests.
  =release.yml= runs on a version tag (=v0.3.1=): it checks the tag against =versionName=, builds
  and signs, checks the signatures, publishes the GitHub release with =docs/release/notes/0.3.1.md= as its
  notes (the APKs only with =PUBLISH_APKS= on), keeps the Play bundle with the run for Play Console,
  and uploads it to Play's testing track when that is set up. What each workflow does and its
  actions' versions: =docs/release/github-actions.org=.
- Use the release build day to day :: Debug Compose builds are noticeably slower to scroll.
- Compile after sideloading :: A sideloaded APK runs without ahead-of-time compilation until Android
  compiles it during idle maintenance, so it can feel laggy at first. To compile it immediately, run
  =adb shell cmd package compile -m speed -f com.mtwabpin.kolahal=.
- After installing :: Run =setup=. It checks the default home app, usage access, notifications,
  notification access, the optional permissions (Do Not Disturb, system settings, calendar, exact
  alarms, and in the full build double-tap lock, contacts and the call log) and unrestricted battery.
  Tapping a line that isn't checked runs its fix, which opens the matching system page.

* Architecture

#+begin_example
MainActivity (HOME) ── TerminalViewModel ── CommandProcessor ──► command groups (terminal/commands/)
   home: TerminalScreen → GuiHome or TtyHome (home.style), the widgets page beside it
   pages: Settings · Scripts · Shaders · Feeds · ScriptEditor · Widgets · Setup · Tour …
                               │
        AppRepository (LauncherApps, all profiles) + AppPrefs (hidden, labels, frecency, aliases)
        UnlockCounter · DeviceStatus · Config · Backup · Shaders
        LogRepository / ScriptRepository / KvStore (kolahal.db, SQLite, WAL) · FeedRepository (feeds.db)
                               │
        ScriptScheduler ──► WorkManager ──► ScriptWorker      [process :script]
                    └────► AlarmManager ─► ScriptRunService   (daily times)
                                both run ScriptRun, under RunWatchdog:
                                             ├─ LuaEngine (LuaJava, Lua 5.4 native)
                                             └─ JsEngine  (quickjs-kt, QuickJS, guard.js)
                                                   └─ HostApi (http, rss, store, widget, tty …)
        ScriptScreenService ◄── home binds it while a script's tty.screen shows   [process :script]

ShaderWallpaper (live wallpaper) ◄── files/wallpaper/state.json ◄── WallpaperWriter (home)   [process :wallpaper]

TextEditorActivity (a task per file, in Recents) ── TextEditorViewModel ── documents/
   opened by: edit · the editor's own menu · another app's "Open with"
   TextDocument (read, save, conflicts) · Drafts (files/editor-drafts) · RecentFiles
#+end_example

- Layers :: Three, each using only those below it: =ui/= (Compose), =terminal/= (the view model, its
  helpers, the command handlers in =terminal/commands/= and the grid's model in =terminal/tty/=), and
  the Model (every other package, =commands/= with the command catalog included). =LayersTest= reads
  the sources and fails when the Model names =ui/=, =terminal/= or =TerminalViewModel=, when
  =terminal/= names =ui/=, when a root file other than =MainActivity= does either, when
  =terminal/tty/= uses =android.graphics= or Compose UI, when =ui/tty/= uses Material 3, and when a
  package isn't in its list of layers.
- Processes :: Home and every page run in the main process. Scripts run in =:script= (WorkManager's
  =RemoteWorkerService=, =ScriptRunService=, =ScriptScreenService=), so a native engine crash can't
  take down the home screen; =RunWatchdog= kills that process when a run can't be stopped from
  inside, 5 s past its timeout. The live wallpaper (=ShaderWallpaper=, Android 13 and newer) runs in
  =:wallpaper=, so a shader that crashes doesn't take home along. =LauncherApp.onCreate= runs
  =startInEveryProcess= (crash reports, notification channels) everywhere and its other steps only
  in the main process (=Singleton.inMainProcess=).
- Across processes ::
  - =:script= and home share =kolahal.db=. After a write, =:script= sends a package-scoped broadcast
    (=LogRepository.ACTION_LOGS_CHANGED=, =WidgetStates.ACTION_CHANGED=, =TodoStore.ACTION_CHANGED=),
    which =LauncherApp.listenToOtherProcesses= hands on. A script sends a command to home with
    =HostApi.ACTION_RUN_COMMAND=.
  - =:script= reads the settings file once, when it starts, so home copies the settings it reads
    (=SharedSettings.KEYS=) to the =shared-settings= scope whenever they change.
  - Home writes what the live wallpaper draws (=WallpaperState=: the shader, its parameters, the
    theme's colors) to =files/wallpaper/state.json= (=WallpaperWriter=), and the wallpaper reads it.
- View model :: =TerminalViewModel= holds what home and the pages show, as state flows, and runs
  commands and actions in order on one serial IO dispatcher. Most of its work is in helpers, each
  reaching it through a small =Host= interface: =PromptActions= (the prompt, history, touch keys,
  instant launch, Enter), =Navigation= (which page is open, and Back), =HomeSession= (leaving home
  and coming back), =LogPager= (the log's page and its reload), =LogSearcher=, =LogLineActions= (taps
  and long-press menus), =HeaderActions=, =RequestActions= (permissions and pickers),
  =ScriptActions=, =ShaderActions=, =BackupActions= and =WidgetActions=. What only the activity can
  do goes back through =TerminalUi= and =UiEvent=.
- Two home styles :: =home.style= decides how =TerminalScreen= draws home: =GuiHome=, or =TtyHome= on a
  character grid (=ui/tty/=), where =tty.suggestions=, =tty.selector=, =tty.keybar=,
  =tty.quick-actions= and =tty.menu= put each of those parts on the grid or leave it as in the GUI
  (=TtyParts=). Both draw the log from one model: =lineModel()= (=terminal/LineModel.kt=) decides
  what a row shows and what can be tapped; the GUI draws it with =LogView= and =LogLineText=, and
  the grid lays it out in cells (=LineLayout=, plain Kotlin in =terminal/tty/=) that =ui/tty/= paints.
  =ParityTest= keeps the two from drifting. The design: [[file:tty-architecture.md][tty-architecture.md]].
- Commands :: =CommandProcessor= (=terminal/commands/=) parses a line and dispatches on its first word
  in one =when (name)= in =execute=. The work is in command groups (=CommandGroup= subclasses:
  =AppCommands=, =SystemCommands=, =LogCommands= …). What each command is (usage, help, other names,
  whether it is sensitive, its section in =help=) is in =commands/CommandCatalog.kt=, in the Model,
  so completion, scripts and the safety checks read the same list.
- The text editor :: A second activity, because a screen inside the launcher's task is lost on Home.
  It shares the editing core (=CodeEditor=, =EditorState=) with the script editor, and reads and
  writes files through the content resolver only: no storage permission.
  [[file:codebase-guide.org::*The text editor: a second window][codebase-guide.org]] has the design.

- Script screens :: =tty.screen= (a script's own full-screen screen) runs in the =:script= process
  once the code has run. =ScreenSession= is the script's side: it waits for home's messages and calls
  the script's functions, each with its own second. Home binds =ScriptScreenService= and plays the
  drawing it gets (=ScreenFrame=) on its grid (=FramePlayer=, through =ScriptScreen=), and sends ticks,
  keys and taps. It sends the next tick only after the last one's frame, so it never waits for a script.
  The run leaves its worker when home shows the screen (=ScreenRuns=), as Android stops a worker after about
  ten minutes; home's binding then keeps the process. A script with =@uses screen= is a command only
  (=ScriptMeta.isScreen=).
- Access :: =ScriptAccess= decides what a run may use: each =@uses= item only once the user allows
  it; the internet and pinning at the top only if the code mentions them (=ScriptMeta.usesInternet=,
  =setsStatus=; pinning stays off until the user pins it), and code from outside that starts using the internet starts with it off.
  =secrets.get= returns a stand-in; =HostApi.fillSecrets= puts the value in a request only for the
  =@secret= line's sites, over https. Lines a script logs keep only =url=, =image=, =copy=, =mono=
  and =gap= from their context, and their buttons (=actions=).
  Each access is in =ScriptAccess.PRIVATE= (it reads data about the person) or =NOT_PRIVATE=, with
  why; =ScriptPrivacyTest= fails on one in neither. A script allowed the internet together with a
  private item gets a warning wherever its access shows or is given (=privateWithInternet=,
  =warning=, =warningHint=); nothing is blocked.
- Run limits :: =HostApi= keeps the run's clock (=sleep= and requests never wait past it), refuses
  side effects once the run is over (=finish=), and caps what one run does: 500 log lines (256 K
  characters), 10 notifications, 20 status-line changes, 20 =widget.show= calls, a 100,000-character
  clip. A script's store holds at most 16 MB in bytes (=KvStore=).
- Lua sandbox ::
  - Fresh state per run. =java=, =io=, =package=, =require=, =debug=, =dofile=, =loadfile= and
    process-level =os= functions are removed, and only text chunks can be loaded.
  - An instruction-count hook, also installed on coroutines, checks the 64 MB memory cap every
    1,000 instructions and the 60 s timeout every 10,000. =pcall=, =xpcall= and
    =coroutine.resume= can't swallow either, and the guards keep their own copies of the functions
    they use, so a script replacing =error= or =string.find= can't switch them off.
  - A C function past the deadline, or memory growing faster than the hook checks (a string
    doubling itself), is stopped by =RunWatchdog= (128 MB of new native memory).
- JS sandbox :: QuickJS with only the bindings above, a 64 MB memory limit and an evaluation timeout.
  =guard.js= (=JsEngine.GUARD=) runs first: every host function takes a plain copy of its arguments,
  at most 64 levels deep, no string over 4 MB, no array or object over 100,000 entries (quickjs-kt's
  native conversion has no depth check and would crash the process), and at most 64 requests or
  sleeps wait at once. =RunWatchdog= stops what the interrupt doesn't reach: built-ins that never
  poll, promise jobs that keep queuing one another.
- Scheduling ::
  - Interval jobs are periodic work, with Android's 15-minute minimum.
  - Each daily time is an AlarmManager alarm (=ScriptAlarms=), exact when Alarms & reminders is
    allowed. Its receiver sets the next day's, then starts =ScriptRunService=, a short foreground
    service in =:script= (in front, as Android requires before a launcher may pause the work
    profile); when Android doesn't allow that, the run goes in the queue like the others.
  - Event runs (=@on=) queue one after another per script (unique work), and an event queued before
    its switch went off doesn't run.
  - Two runs of one script never overlap, however each started (timer, daily time, event, the
    prompt, a pinned line's refresh): =ScriptRun= holds a lock per script in the =:script= process,
    and the second waits for the first.
- UI work :: One serial IO dispatcher with an exception handler, so a failed action is logged
  instead of crashing home. Log rows are pre-built off the main thread and rendered as immutable
  rows with cached text.

* Repository layout

A map for reviewing the code or finding where to make a change. Everything lives in one Gradle
project; the app's code is under =app/src/main/java/com/mtwabpin/kolahal/=, and the package table
gives paths from there.

** How a typed line flows

1. The prompt (=ui/home/Prompt.kt=, or =ui/tty/TtyPrompt.kt= on the grid) shows =TerminalViewModel.input=.
   Every keystroke goes to =PromptActions.onInputChange=, and =Completer.suggestions()= builds the
   suggestion list (commands, apps, then per-command arguments, usage-line options and history).
   With =launch.instant= on, =InstantRun.target= may launch an app or run the line without Enter.
2. Enter calls =TerminalViewModel.submit= (=PromptActions.submit=), which queues
   =CommandProcessor.run(line)= on the view model's single IO dispatcher. Kolahal's own taps (a
   tap-to-run log line, a header part, a button) go through =runCommand=, which runs the line as
   given (=expand = false=) and even when its command is turned off (=fromApp=).
3. =run= logs the command line (not =fresh=, not a line that carries a script secret, and the same
   line again joins the one before) and marks what follows as its output (=withCause=). =runLogged=
   writes that output in one batch, expands aliases (=Aliases=) and splits =|= pipes (=Pipes=: the
   first stage's output is captured, then filtered). =execute= takes ~=~ as the calculator, opens
   an app for a command turned off (=commands.off=), then dispatches on the first word in one =when=:
   each branch calls a command group (=AppCommands.run=, =systemCommands.cal= …) or the UI
   (=ui.openScreen=). The =else= runs a script command (=ScriptCommands.runCommand=) or launches the
   best-matching app (=fallbackLaunch=). An exception becomes an error line.
4. Commands write their output with =LogRepository.add= (=out=, =info=, =error= and =fix= in
   =CommandGroup=). Each line carries a =LogContext= (package, URL, phone number, run command …) that
   decides what a tap or long-press on it does later (=LogLineActions.onTap= / =actionsFor=).
5. The repository bumps its =version=. While home shows, the view model reloads (=LogPager.reload=;
   a burst of changes is one reload), and =buildRows= (=terminal/LogRows.kt=) groups and dims the
   lines and adds day dividers off the main thread, into =TerminalViewModel.rows=.
6. Each row is drawn from one =LineModel= (=lineModel()=, =terminal/LineModel.kt=): in the GUI style
   by =LogLine= (=ui/home/LogView.kt=, its text built in =ui/home/LogLineText.kt=); on the grid by =TtyLog=
   (=ui/tty/TtyLog.kt=), which lays the model out in cells with =LineLayout= and paints them. The
   script editor's reference draws its log examples with the same two (=LinesPreview=, which calls
   =LogLine= or =TtyLinesShown=).

Background sources (scripts, feeds, notifications, app events) skip steps 1–3 and write to the log
directly. Scripts do it from the =:script= process; a broadcast tells the UI process to reload.

** Keeping a pull request out of others' way

Most conflicts come from a few shared lists, not from the code a feature adds. To keep yours small:

- A new family of commands goes in its own file in =terminal/commands/= (as =terminal/commands/WebCommands.kt=
  is), extending =CommandGroup=. The shared files then only gain a line each. Don't add its code to =CommandProcessor=
  or =TerminalViewModel=: the view model already holds a lot, so new state and actions go in a small
  class with a =Host= interface, as =ScriptActions= and =LogLineActions= have.
- Lists are one entry per line: =Keys.ALL=, =CommandCatalog.COMMANDS=, =HELP_SECTIONS=,
  =Stores.PREFS= and the pages in =SettingsCatalog=. Keep them that way, and add yours beside related
  entries rather than at the end, where everyone else is adding too.
- A new script API goes in =HostApi= as usual, but keep long logic in its own file and call it from there.
- Leave these to the maintainer, who sets them when releasing: the version in =app/build.gradle.kts=
  and =site/package.json=, =docs/release/notes/=, and the coverage figure in =README.org=.
- Do one thing per pull request, and don't reformat or move code you aren't otherwise changing.
- A file is worth splitting when it holds separate concerns that change for different reasons, not
  because it's long. =ui/home/AppSelector.kt= is one long gesture: it stays whole. =script/HostApi.kt=
  is one API, but the run's log buffer (=RunLog=) and its secrets (=RunSecrets=) change for their
  own reasons, so they have files of their own and =HostApi= calls them.
