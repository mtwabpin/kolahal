#+TITLE: Working on Kolahal
#+STARTUP: showall

A quick reference for changing the code: building, how the parts fit, where things are, and the
usual changes. [[file:codebase-guide.org][codebase-guide.org]] is the long, guided tour; [[file:release/README.org][release/]] covers signing and
publishing.

* Build

#+begin_src sh
./gradlew :app:assembleDebug              # debug APK ("Kolahal debug", package suffix .debug)
./gradlew :app:assembleRelease            # R8-optimised; signed with keystore.properties or the debug key
./gradlew :app:bundlePlay                 # Google Play: release without accessibility, the call log, reading contacts and update
./gradlew -PplayApk :app:assemblePlay     # the same as an APK, signed with the release key (GitHub releases)
./gradlew :app:testDebugUnitTest          # JVM tests
./gradlew :app:connectedDebugAndroidTest  # engines, sandbox, timeouts, :script process, commands
#+end_src

- Toolchain :: AGP 9.4.1, Gradle 9.8.2, Kotlin 2.4.21, compileSdk 37, targetSdk 37, minSdk 28,
  Jetpack Compose. Material 3 is pinned to =1.5.0-beta01= for the Expressive components; 1.5.0 stable
  isn't released yet (checked 2026-10-17), switch =material3= in =gradle/libs.versions.toml= when it is.
  The NDK is pinned (=ndkVersion=, 28.2.13676358, AGP's default): it strips the native libraries
  (Lua, QuickJS) and keeps their symbols in the Play bundle; the workflows install the same one.
- Baseline profile :: =app/src/release/generated/baselineProfiles/= is generated by the
  =:baselineprofile= module (cold start with notification access on, typing, help/apps output,
  log scroll, settings). Regenerate with only an emulator attached (it reinstalls the app and
  drives every connected device): =./gradlew :app:generateReleaseBaselineProfile=.
- Signing :: =keystore.properties= (git-ignored) names the release key, which signs the APKs
  (=storeFile=, =storePassword=, =keyAlias=, =keyPassword=), and the upload key, which signs the Play
  bundle (=uploadStoreFile=, =uploadStorePassword=, =uploadKeyAlias=, =uploadKeyPassword=); the
  =KOLAHAL_RELEASE_*= and =KOLAHAL_UPLOAD_*= environment variables do the same in CI.
  =tools/make-keys.sh= makes both keys and the file; =tools/make-keys.sh --secrets= stores them for
  GitHub Actions. Without a release key the APK is signed with the debug key; without an upload
  key the bundle stays unsigned. Why there are two keys, and the whole release setup:
  =docs/release/README.org=.
- GitHub Actions :: =build.yml= runs the unit tests and builds both on every push.
  =release.yml= runs on a version tag (=v0.3.1=): it checks the tag against =versionName=, builds
  and signs, checks the signatures, publishes the GitHub release with =docs/release/notes/0.3.1.md= as its
  notes, and keeps the Play bundle with the run for Play Console. What each workflow does and its
  actions' versions: =docs/release/github-actions.org=.
- Use the release build day to day :: Debug Compose builds are noticeably slower to scroll.
- Compile after sideloading :: A sideloaded APK runs without ahead-of-time compilation until Android
  compiles it during idle maintenance, so it can feel laggy at first. To compile it immediately, run
  =adb shell cmd package compile -m speed -f com.mtwabpin.kolahal=.
- After installing :: Run =setup=. It checks the default launcher, Usage Access, notifications and
  battery optimisation, and each unchecked line fixes itself when tapped.

* Architecture

#+begin_example
MainActivity (HOME) ── TerminalViewModel ── CommandProcessor
   screens: Terminal (+ widgets page) · Settings · Scripts · Feeds · ScriptEditor · Widgets · Setup
                               │
        AppRepository (LauncherApps, all profiles) + AppPrefs (hidden, labels, frecency, aliases)
        UnlockCounter · DeviceStatus · Config · Backup
        LogRepository / ScriptRepository / KvStore (SQLite, WAL)
                               │
        ScriptScheduler ──► WorkManager ──► ScriptWorker      [process :script]
                    └────► AlarmManager ─► ScriptRunService   (daily times)
                                both run ScriptRun, under RunWatchdog:
                                             ├─ LuaEngine (LuaJava, Lua 5.4 native)
                                             └─ JsEngine  (quickjs-kt, QuickJS, guard.js)
                                                   └─ HostApi (http, rss, log, notify, store, status)
#+end_example

- Isolation :: Scripts run in a separate =:script= process (=RemoteCoroutineWorker=, or
  =ScriptRunService= at a daily time), so a native engine crash can't take down the home screen.
  Results come back through the shared database plus a package-scoped broadcast. =RunWatchdog= kills
  that process when a run can't be stopped from inside, 5 s past its timeout.
- Access :: =ScriptAccess= decides what a run may use: each =@uses= item only once the user allows
  it; the internet and the header line only if the code mentions them (=ScriptMeta.usesInternet=,
  =setsHeader=), and code from outside that starts using the internet starts with it off.
  =secrets.get= returns a stand-in; =HostApi.fillSecrets= puts the value in a request only for the
  =@secret= line's sites, over https. Lines a script logs keep only =url=, =image=, =copy= and =mono=.
- Run limits :: =HostApi= keeps the run's clock (=sleep= and requests never wait past it), refuses
  side effects once the run is over (=finish=), and caps what one run writes: 500 log lines,
  10 notifications, 20 header-line changes, a 100,000-character clip, a store of 16 MB in bytes.
- Lua sandbox ::
  - Fresh state per run. =java=, =io=, =package=, =require=, =debug=, =dofile=, =loadfile= and
    process-level =os= functions are removed, and only text chunks can be loaded.
  - An instruction-count hook, also installed on coroutines, checks the 64 MB memory cap every
    1,000 instructions and the 60 s timeout every 10,000. =pcall=, =xpcall= and
    =coroutine.resume= can't swallow either, and the guards keep their own copies of the functions
    they use, so a script replacing =error= or =string.find= can't switch them off.
  - A C function past the deadline, or memory growing faster than the hook checks (a string
    doubling itself), is stopped by =RunWatchdog= (128 MB of new native memory).
- JS sandbox :: QuickJS with only the bindings above, a 64 MB memory limit and an evaluation timeout.
  =guard.js= (=JsEngine.GUARD=) runs first: every host function takes a plain copy of its arguments,
  at most 64 levels deep, no string over 4 MB, no array or object over 100,000 entries (quickjs-kt's
  native conversion has no depth check and would crash the process), and at most 64 requests or
  sleeps wait at once. =RunWatchdog= stops what the interrupt doesn't reach: built-ins that never
  poll, promise jobs that keep queuing one another.
- Scheduling ::
  - Interval jobs are periodic work, with Android's 15-minute minimum.
  - Each daily time is an AlarmManager alarm (=ScriptAlarms=), exact when Alarms & reminders is
    allowed. Its receiver starts =ScriptRunService=, a short foreground service in =:script= (in
    front, as Android requires before a launcher may pause the work profile), and sets the next day's.
  - Event runs (=@on=) queue one after another per script (unique work), and an event queued before
    its switch went off doesn't run.
- UI work :: One serial IO dispatcher with an exception handler, so a failed action is logged
  instead of crashing home. Log rows are pre-built off the main thread and rendered as immutable
  rows with cached text.

** How a typed line flows

1. =ui/Prompt.kt= shows the prompt. Every keystroke updates =TerminalViewModel.input=, and
   =Completer.suggestions()= builds the suggestion list (commands, apps, then
   per-command arguments, usage-line options and history).
2. Enter (or =InstantRun=, a tap on a suggestion or a log line) calls =CommandProcessor.run(line)= on
   the view model's single IO dispatcher.
3. =run= logs the command line, expands aliases, splits =|= pipes (=Pipes=), then =execute= dispatches
   on the first word in one =when=. Each branch calls a helper in =CommandProcessor= or a command
   group (=AppCommands=, =ScriptCommands=, =ControlCommands= and the other =*Commands= classes), a
   script command, or an app launch as the fallback.
4. Commands write their output with =LogRepository.add= (=info=, =error=, =out= helpers). Each line
   carries a =LogContext= (package, URL, phone number, run command …) that decides what a tap or
   long-press on it does later (=LogLineActions.onTap= / =actionsFor=).
5. The repository bumps its version; the view model reloads, =LogRows.buildRows= groups and dims the
   lines off the main thread, and =LogView.LogLine= renders them.

Background sources (scripts, feeds, notifications, app events) skip steps 1–3 and write to the log
directly. Scripts do it from the =:script= process; a broadcast tells the UI process to reload.

** Common changes

- New command :: add a =CommandSpec= to =CommandCatalog.COMMANDS= (help and completion read it), a
  branch in =CommandProcessor.execute= (or in its group's =run=, such as =AppCommands.run= with its
  =NAMES=), and the name to a =HELP_SECTIONS= group. If it changes state, costs money or leaves the
  launcher, add it to =InstantRun.SENSITIVE= too, so it never runs without Enter or from a script.
  If a build leaves it out, add it to =FEATURE_COMMANDS=. Argument completion: options in the usage line complete
  automatically; anything smarter goes in =Completer.argSuggestions=.
- New setting :: define it in =Keys= (=data/Keys.kt=) and add it to =Keys.ALL=. Put it in a page in
  =ui/SettingsCatalog.kt= (=CATEGORIES=) with a title in =TITLES=; unplaced keys appear under "More".
  Document it in =site/src/content/docs/reference/config.md=.
- New script API :: add it to =HostApi=, bind it in both =LuaEngine= and =JsEngine=, and describe it in
  =ApiDocs= (=ApiDocsTest= checks that the names match). A new JavaScript namespace goes into
  =guard.js='s =spaces= list (=JsEngine.GUARD=), and an async function that waits is marked so in
  the loop that installs the guards (as =http= and =rss= are): otherwise its arguments reach the
  native conversion unchecked, or it escapes the cap on calls waiting at once. A call that reaches outside
  checks the script's access (=may=), and one with an effect calls =live()= first.
- Log line behaviour :: the tap and long-press logic is in =LogLineActions.onTap= / =actionsFor=,
  keyed on =LogContext= values. Rendering is in =ui/LogView.kt=, and the line's text in =ui/LogLineText.kt=.
- New action on the script screens :: it goes in =ScriptActions=, not the view model.

** Keeping a pull request out of others' way

Most conflicts come from a few shared lists, not from the code a feature adds. To keep yours small:

- A new family of commands goes in its own file (=terminal/WeatherCommands.kt=), extending
  =CommandGroup=. The shared files then only gain a line each. Don't add its code to =CommandProcessor=
  or =TerminalViewModel=: the view model already holds a lot, so new state and actions go in a small
  class with a =Host= interface, as =ScriptActions= and =LogLineActions= have.
- Lists are one entry per line: =Keys.ALL=, =CommandCatalog.COMMANDS=, =HELP_SECTIONS=,
  =InstantRun.SENSITIVE= and =SettingsCatalog=. Keep them that way, and add yours beside related
  entries rather than at the end, where everyone else is adding too.
- A new script API goes in =HostApi= as usual, but keep long logic in its own file and call it from there.
- Leave these to the maintainer, who sets them when releasing: the version in =app/build.gradle.kts=
  and =site/package.json=, =docs/release/notes/=, and the coverage figure in =README.org=.
- Do one thing per pull request, and don't reformat or move code you aren't otherwise changing.
- A file is worth splitting when it holds separate concerns that change for different reasons, not
  because it's long. =ui/AppSelector.kt= is one long gesture, and =script/HostApi.kt= is one API:
  they stay whole.
