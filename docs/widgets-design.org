* How to read this

This is a proposal. Nothing here is built. It was written on 14 November 2026 against the =0.5.8=
branch (commit =5dbb9dd9=). Where it and the code disagree, the code wins.

- [[*Summary][Summary]] is the whole idea on one page.
- [[*Decisions][Decisions]] answers the eight design questions, each with its reasons.
- [[*The catalog][The catalog]] lists what to choose from: 12 widget kinds and 25 ready-made widgets.
- [[*What changes in the code][What changes in the code]] names the files.
- [[*Phased plan][Phased plan]] says what to build first.
- [[*Open questions][Open questions]] are for the owner. Each has a recommended answer.

* Summary

- *What it is.* A script calls =widget.show{…}= with a small description: "a big number 24°C, the
  label Sunny, two smaller numbers". Kolahal checks the description and draws it as a card, in
  Material 3 Expressive, on the widgets page.
- *No UI code from scripts.* A script picks one of a fixed set of /kinds/ (stat, list, chart, …)
  and fills in its fields. Kolahal owns every pixel, every colour and every tap.
- *Where.* On Kolahal's own widgets page, in the same list as other apps' widgets. Not on other
  launchers' home screens in the first build.
- *How data moves.* The script runs in =:script= as today. Kolahal stores the checked description
  in =kolahal.db=. The main process reads it and draws. The main process never waits for a script.
- *Refresh.* The script's own timers and events (=@every=, =@at=, =@on=), a tap, and "the page is
  showing and the content is old". Clocks and countdowns tick in Kolahal, with no script run.
- *Taps.* A tap runs /the same script/ again with arguments, or opens a web link. A script can
  never put a terminal command behind a tap. Commands you pick yourself live in a built-in
  Shortcuts widget.
- *Permission.* Placing a widget is the permission, like pinning a status line. No script places
  itself. Everything else uses the access a script already has (=@uses=, internet, secrets).
- *Two feeders, one renderer.* The same cards can also be filled by Kolahal itself, for data that
  must be live or that scripts may not touch (now playing, battery, todos, your own commands).
- *First build.* 6 kinds and 12 ready-made widgets. 7 of the 12 are library scripts that exist
  today and gain one =widget.show= call.

* Words used here

| Word            | Meaning                                                                                  |
|-----------------+------------------------------------------------------------------------------------------|
| app widget      | Another app's Android widget, hosted on the widgets page. This exists today.              |
| script widget   | New: a card that Kolahal draws from a script's description.                              |
| built-in widget | New: a card that Kolahal draws from its own data (battery, todos). No script is needed.  |
| kind            | One of the card types Kolahal can draw: =stat=, =list=, =chart= and so on.               |
| description     | The table (Lua) or object (JavaScript) a script hands to =widget.show=.                  |
| state           | The last checked description of a widget, plus when it was set and the last error.       |
| placed          | The user added the widget to the widgets page.                                           |
| role            | A colour by meaning, not by value: =accent=, =good=, =warn=, =bad=, =info=, =link=, =muted=, =text=. |

* What exists today, and what it means for the design

These facts come from the code. Each one limits or helps the design.

- *The widgets page* is a Compose page beside the log ([[src:ui/HostedWidgets.kt::fun WidgetPanel][WidgetPanel]]).
  - It lays widgets out in 12 columns, with a height in dp for each ([[src:widgets/WidgetModel.kt::object WidgetLayout][WidgetLayout]],
    [[src:ui/HostedWidgets.kt::internal fun WidgetFlow][WidgetFlow]]). It has no cells.
  - A placed widget is a [[src:widgets/WidgetModel.kt::data class PlacedWidget][PlacedWidget]]: an AppWidget id and a provider. The stored form
    ([[src:widgets/WidgetModel.kt::object WidgetCodec][WidgetCodec]]) drops a line whose provider has no =/=.
  - The pager keeps the widgets page composed while the log shows (~beyondViewportPageCount = 1~
    in =HomePager=). So "the page is composed" does not mean "the user sees it".
- *Status lines* are the nearest thing to a widget today ([[src:data/StatusLines.kt::object StatusLines][StatusLines]]).
  - =status(text, opts)= stores a line by script name in the =kv= table.
  - It shows at the top of home only after the user pins the script. No script pins itself.
  - =opts.refresh= runs the script again while the line shows, as unique work that is never
    queued twice ([[src:script/ScriptScheduler.kt::fun refreshPinned][refreshPinned]]). A failing refresh reports its error once.
  - The design below copies this pattern for widgets.
- *Taps from scripts are narrow on purpose.*
  - A script's log line keeps only =url=, =image=, =copy=, =mono= and =gap= ([[src:script/HostApi.kt::private fun safeCtx][safeCtx]]). The
    =run= key is dropped, so a script can't plant a one-tap command.
  - Buttons under a line (=ctx.actions=) run only the same script again, with arguments and
    =event.name= ="action"= ([[src:terminal/TerminalViewModel.kt::fun runLineAction][runLineAction]]).
  - =launcher.run= works only in a run the user started, needs =@uses commands=, and refuses
    sensitive commands. =torch=, =volume=, =dnd=, =media=, =todo=, =note=, =remind= and =widget=
    are all sensitive ([[src:commands/InstantRun.kt::fun isSensitive][InstantRun.isSensitive]], [[src:commands/ControlSpecs.kt::val SENSITIVE][ControlSpecs.SENSITIVE]]).
- *Scripts can't see the main process.* =MediaRepository.nowPlaying=, =DeviceStatus.status= and
  =UnlockCounter.today= are flows in the main process. A script reads the battery and the network
  itself (=device.battery()=, =device.network()=). It can't read what is playing.
- *Scripts have no call for Kolahal's own lists.* There is no script function for todos, notes,
  reminders, the calendar, or the built-in feed reader.
- *Timers have a floor.* =@every= can't run more often than every 15 minutes (WorkManager). A
  script can't tick a clock.
- *Access is checked in code.* =internet= is on when the code mentions =http=, =rss=, =url= or
  =image=. The words =status= and =notify= switch on other items
  ([[src:script/ScriptMeta.kt::fun usesInternet][ScriptMeta]]). So a description must not use fields named =status= or =notify=.
- *The GUI kit is there.* =GuiTheme= builds a Material scheme from the terminal palette, in its dark
  and light version ([[src:ui/GuiTheme.kt::fun schemeFrom][schemeFrom]]). Material 3 =1.5.0-rc01= has the Expressive
  parts this design names. They were checked in the library's sources: =LoadingIndicator=,
  =LinearWavyProgressIndicator=, =CircularWavyProgressIndicator=, =ButtonGroup=, =ToggleButton=,
  =MaterialShapes= with =toShape()=.

* Decisions

** 1. Where widgets show

*Recommended for the first build: Kolahal's own widgets page only.*

| Place                                   | For                                                                                           | Against                                                                                                             |
|-----------------------------------------+-----------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------|
| Kolahal's widgets page (Compose)        | The page, its layout, its edit screen and its backup exist. Full Expressive shapes and motion. Kolahal can tick clocks itself. Taps are instant. | Shows only while Kolahal is the launcher. That is the product.                                                      |
| Home-screen widgets for other launchers | Reaches people who use another launcher.                                                      | See the list below.                                                                                                 |
| The pinned header                       | Exists. Always in view.                                                                       | One line of text and a bar. It stays as it is.                                                                      |

Why not home-screen widgets (Glance or RemoteViews) now:

- They can't use Compose Material 3 Expressive. Glance has its own small set of parts: no shaped
  badges, no press morph, no springs. Charts would be pictures made in advance.
- They can't share the card code. It would be a second renderer for every kind.
- Kolahal's users have Kolahal as home. A widget for /another/ launcher helps few of them.
- =@on= events are received in the UI process ([[src:script/TriggerDispatcher.kt::class TriggerDispatcher][TriggerDispatcher]]). When Kolahal is not
  the launcher, that process may not run, so event widgets would be late.
- It needs a new dependency (=androidx.glance=) and a new receiver.

The description is data, not code. So a second renderer can be added later without changing any
script: it would read the same stored state. This is phase 4, and only if someone asks.

One small bridge to the pinned header comes free: a *Status card*. Any script that calls
=status()= today can be placed as a card that shows its line, its bar and its colour. No script
changes. See [[*Ready-made widgets][the catalog]].

** 2. How a script defines a widget

Three parts: a directive, a call and a description.

*** The directive

#+begin_example
-- @widget <kind> [<size>]        Lua
// @widget <kind> [<size>]        JavaScript
#+end_example

- It says "this script has a widget". The widget picker lists the script.
- =<kind>= is the default kind. The picker draws a sample of it before the script has ever run.
- =<size>= is the size it gets when placed: =1x1=, =2x1=, =2x2=, =4x1=, =4x2= or =4x4=. Without
  one, the kind's default is used.
- Without this line, =widget.show= is an error that says to add it. This is the rule =@uses= has.
- One script has one widget in the first build. See [[*Open questions][Open questions]].

*** The calls

| Call                | What it does                                                                                              |
|---------------------+-----------------------------------------------------------------------------------------------------------|
| =widget.show(desc)= | Checks =desc= and stores it as this script's widget. Returns true when the widget is placed, else false.  |
| =widget.clear()=    | Removes the content. The card then shows "Nothing to show".                                               |
| =allowed("widget")= | True when the user placed this script's widget. A script can skip work when it is false.                  |

- =event.name= is ="widget"= in a run the widgets page asked for (just placed, old content, a
  =refresh=).
- =event.name= is ="action"= in a run a tap started. The tap's arguments are in =args=, and
  =event.label= is the tapped item's label. This is what a button under a log line does today, so
  one handler serves both. =event.widget= is true for a tap on a widget.
- =widget.show= works only in saved scripts, as =status= does. Code typed at the prompt gets a
  line that says so.
- A run may call =widget.show= at most 20 times. The same description again changes nothing.
- A wrong description is an error in the script, with the line number, like any script error.
  Tapping the error opens the editor there.

*** The description

Every kind takes these fields. All are optional.

| Field        | Value                | Meaning                                                                                       |
|--------------+----------------------+-----------------------------------------------------------------------------------------------|
| =kind=       | a kind's name        | Which card to draw. Default: the =@widget= line's kind.                                       |
| =title=      | text, up to 40       | The small heading. Default: the script's =@title=.                                            |
| =icon=       | text, up to 4        | An emoji or a letter. Kolahal draws it in a shaped badge.                                     |
| =color=      | a role               | The colour of the badge, bar or chart. Default: =accent=.                                     |
| =tap=        | an action            | What a tap on the card does. Default: refresh. See [[*4. Interaction][Interaction]].         |
| =staleAfter= | seconds, 60 to 604800 | How long the content counts as current. Default: see [[*3. Data flow and refresh][Refresh]]. |
| =refresh=    | seconds, 10 to 3600  | Run again this often while the widget is on screen. The same limits as =status=.              |

Each kind adds its own fields. They are in [[*Widget kinds][the catalog]].

Rules for every description:

- *Typed.* Each field has one type: text, number, true or false, a role, a list, an action. A
  number where text is expected becomes text. Anything else is an error that names the field and
  says what to pass.
- *Closed.* An unknown field is an error that lists the known ones. A typo such as =colour= does
  not pass unseen. =fmt.bar= and =status= already work this way.
- *Bounded.* Text is cut with "…" at its limit. A list keeps its first items, up to the kind's
  limit. More buttons than a kind allows is an error. The whole description is at most 32 KB.
- *Plain text.* Styles from =fmt= are removed. The first build draws plain text only.
- *Colours by role only.* A script never gives a colour value. The theme picks the colour, in its
  dark and its light version, so every widget reads on every theme.
- *Safe names.* No field is a Lua keyword (so not =end=, =until= or =in=), and none is =status= or
  =notify=. Links are in fields named =url= and =image=, so the internet switch covers them. A unit
  test checks this list.

*** Example in Lua: a number

#+begin_src lua
-- @title Weather
-- @widget stat 2x1
-- @every 1h
-- @option city "" City; empty: your IP address's location

local r = http.get("https://wttr.in/" .. options.city .. "?format=%l|%c|%t|%C|%h")
if not r.ok then error("wttr.in answered HTTP " .. r.status) end
local place, icon, temp, sky, humidity = r.body:match("^(.-)|(.-)|(.-)|(.-)|(.-)$")

widget.show{
  title = place,
  icon = icon,
  value = (temp:gsub("^%+", "")),
  label = sky,
  more = { { value = humidity, label = "humidity" } },
  staleAfter = 2 * 3600,
}
#+end_src

When the request fails, the script stops with an error. The card keeps the last good content and
says "Failed 10:42" under it.

*** Example in JavaScript: a list

#+begin_src js
// @title Headlines
// @widget list 4x2
// @every 1h
// @option url https://hnrss.org/frontpage The feed to show

const feed = await rss.fetch(options.url);
widget.show({
  title: feed.title,
  items: feed.items.slice(0, 8).map((it) => ({
    title: it.title,
    tap: { url: it.link },
  })),
});
#+end_src

*** Example with a tap: count glasses of water

#+begin_src lua
-- @title Water
-- @widget progress 2x1
-- @option goal 8 Glasses a day

local today = os.date("%Y-%m-%d")
local n = tonumber(store.get(today) or "0")
if event and event.name == "action" and args[1] == "add" then
  n = n + 1
  store.set(today, tostring(n))
end
local goal = tonumber(options.goal) or 8
widget.show{
  value = n, max = goal,
  text = n .. " / " .. goal,
  color = n >= goal and "good" or "accent",
  tap = { args = "add", label = "Add a glass" },
}
#+end_src

This widget has no timer. It runs when it is placed, when it is tapped, and when the page shows it
with old content.

*** Example where Kolahal does the ticking

#+begin_src lua
-- @widget countdown 2x1
widget.show{ title = "Goa trip", to = os.time{ year = 2026, month = 12, day = 20, hour = 0 } }
#+end_src

The script runs once. Kolahal counts the days, hours and seconds itself.

*** The same file on an older Kolahal

A library script that gains a widget keeps working on a version without widgets:

- An older Kolahal ignores the unknown =@widget= line.
- The script guards the call: ~if widget then widget.show{…} end~ in Lua,
  ~if (typeof widget !== "undefined") …~ in JavaScript. The library scripts already do this for
  =fmt.bar= and =fmt.stats=.
- So no =@requires= line has to change.

** 3. Data flow and refresh

*** The flow

#+begin_example
 :script process                          kolahal.db (kv table)            main process
 ───────────────                          ─────────────────────            ────────────
 a run: timer, event, tap, refresh
   └ widget.show(desc)
       └ HostApi.widgetShow
           ├ WidgetSpec.parse   types, limits, secrets masked, links checked
           └ WidgetStates.put ─────────▶  scope "widget"                       WidgetStates.versionOf(name)
 the run ends (ScriptRun)              ── one message per run ─────────▶      └ the card re-reads
   └ ok, or the error ────────────────▶  scope "widget.meta"                      their own state

                    ◀──── a tap or a refresh request, queued with WorkManager ────
#+end_example

1. The script calls =widget.show(desc)=.
2. =HostApi= checks it in the =:script= process. So a mistake is a script error with a line number.
3. The checked description is stored as JSON, by script name, in a new =kv= scope.
4. A package-private message tells the main process, as the log's message does today.
5. The main process reads the state on an IO thread and decodes it again. It never trusts stored
   JSON: anything it can't read shows as "widget unavailable".
6. The card redraws.

*** The stored state

Two scopes, keyed by script name:

- =widget=: the description, as checked JSON with a format number.
- =widget.meta=: written by Kolahal, never by the script: when the content was last set, when a
  run was last tried, and the last error (masked).

Rules:

- Kolahal writes the state only for a placed widget. For a widget that isn't placed,
  =widget.show= checks the description and returns false. So nothing private waits in the database
  for a widget nobody sees.
- A description equal to the stored one is not written again. Only its time moves.
- The content's time moves only when =widget.show= is called. A run that works but never calls it
  (=weather Paris= typed at the prompt) changes nothing on the card.
- A card says "Failed" after a failed timer, daily, event, ="widget"= or tap run. A failed command
  you typed shows its error in the log, as today, and leaves the card alone. The next
  =widget.show= clears the error.
- The state is a cache. It may hold private text, and a run makes it again. So it does not go
  into backups (see [[*Backups][Backups]]).
- The state is removed when the script is deleted, switched off, or changed from outside, as its
  status line is. A new script that takes an old name starts empty.

*** The message between the processes

Do /not/ reuse =LogRepository.onStatusChanged()=. It raises the log's version, and that makes the
view model read the log again. Widgets get their own message and their own counter:

- =:script= sends =WIDGETS_CHANGED= (package-private, like =LOGS_CHANGED=).
- It names the widget. =LauncherApp= receives it and raises that widget's number (=WidgetStates.versionOf=).
- A run stores quietly and sends one message when it ends (=ScriptRun.widgetEnd=), not one per =widget.show=.
  A =widget.show= early in a long run is drawn when the run ends.
- Each card collects only its own number, and only while home is visible.

*** What starts a run

| Trigger                    | How                                                                                             | =event.name=            |
|----------------------------+-------------------------------------------------------------------------------------------------+-------------------------|
| The script's timer         | =@every=, as today. 15 minutes at the fastest.                                                  | none                    |
| A daily time               | =@at=, as today.                                                                                | ="at"=                  |
| A device event             | =@on=, as today. At most once in 30 seconds for each event.                                     | the event               |
| The widget was just placed | One run at once.                                                                                | ="widget"=              |
| The page shows old content | When the widgets page becomes the page in view, each widget older than its =staleAfter= runs once. | ="widget"=           |
| =refresh= in the description | While the widget is in view, run again that often.                                            | ="widget"=              |
| A tap with arguments       | See [[*4. Interaction][Interaction]].                                                           | ="action"=              |
| An option changed          | The script's sheet or =script set= changed an =@option= of a placed widget.                     | ="widget"=              |
| "Refresh" in the card's menu | Long-press the card.                                                                          | ="widget"=              |

- "In view" means: the pager has settled on the widgets page, and home is on screen. Being
  composed is not enough, because the pager keeps the page composed beside the log.
- A ="widget"= run and a pinned line's refresh share one queue per script (=script-<id>-refresh=). A new
  request of the same kind is dropped while one waits or runs; the other kind waits behind it.
  A script that goes online waits for a network.
- A ="widget"= run is quiet, like a pinned line's refresh. What it returns isn't logged. A failure
  is logged once, until a run works again.
- The script's own =log()= lines /are/ still logged in these runs. A library script skips them
  when =event.name= is ="widget"=. This is the rule pinned lines have, so there is one rule.
- Default =staleAfter=: twice the script's interval. 26 hours for a script with only daily times.
  One hour for a script with no timer.

A script with no timer at all is a good widget: it runs only when you look at it, so it uses no
battery in the background.

*** How each state looks

| State                          | What the card shows                                                                                     |
|--------------------------------+---------------------------------------------------------------------------------------------------------|
| No content yet                 | The title and a =LoadingIndicator= (the Expressive shape that changes form).                            |
| Current                        | The content. No footer.                                                                                 |
| Refreshing, with content       | The content stays. A small indicator in the corner, shown only after 400 ms, so a fast run doesn't flash. |
| Old (past =staleAfter=)        | The content stays readable. A footer says its age: "2 h ago". Nothing is dimmed.                        |
| Failed, with content           | The content stays. The footer says "Failed 10:42" in the error colour. A tap on the footer tries again. |
| Failed, no content             | A short message (the error's first line, with secrets masked) and two buttons: Retry, Open script.      |
| Offline                        | For a script that goes online: "Offline · 2 h ago". The run waits for a network. No endless spinner.    |
| The script is off              | "Script is off". A tap opens Scripts, where turning it on shows its access. No run is asked for.       |
| A key is missing               | "Needs WAQI_TOKEN" and an Add key button, as its card in Scripts has.                                   |
| Access is off                  | "Internet is off for this script" and an Allow button.                                                  |
| The script was deleted         | "Script removed". A tap opens the Widgets screen, where it can be removed.                              |
| The script has no =@widget=    | "Script has no widget now". A tap opens Scripts. No run is asked for.                                   |
| Nothing to show (=widget.clear=) | The title and "Nothing to show".                                                                      |

The words come from Kolahal, never from the script, except the content and the error's first line.

** 4. Interaction

*** What a tap can do

An /action/ is a small table with exactly one of these:

| Action                    | What happens                                                                                  | Build       |
|---------------------------+-----------------------------------------------------------------------------------------------+-------------|
| ~{ args = "add 1" }~      | This script runs again with these arguments. =event.name= is ="action"=.                      | First build |
| ~{ url = "https://…" }~   | The web link opens.                                                                           | First build |
| ~{ app = "com.example" }~ | The app opens. Needs =@uses apps=. Never an app in the private space.                         | Phase 2     |

An action can also have:

- =label=: what a screen reader says for it. Up to 24 characters.
- ~page = "log"~, with =args=: home turns to the log after the tap. Use it for a run that prints,
  such as the full weather report.

Where actions go:

- =tap= on the card: the whole card.
- =tap= on an item of a =list=, =buttons= or =toggles= widget.
- No =tap= on the card means "refresh": a quiet ="widget"= run.

*** Three paths for a tap, and who may use each

1. *Run the same script again* (~{ args }~). Any script widget.
   - It is the path buttons under a log line use, with the same limits: arguments up to 200
     characters, at most one run in 2 seconds for each item.
   - The run counts as started by the user. So =launcher.run= works in it, under its rules today:
     =@uses commands= allowed, no sensitive command, no secret in the command, and a command that
     sends words to a website needs the internet switch.
2. *Open a link or an app* (~{ url }~, ~{ app }~). Any script widget.
   - A link passes the check a log line's link passes: web links only, the internet switch must be
     on, and no secret goes to a site its =@secret= line doesn't name.
   - An app is looked up when you tap, among the apps the script may see (=apps.list=).
3. *Run a command you picked yourself.* Only the built-in Shortcuts widget.
   - You type or pick each command in the Widgets screen, as you set a gesture's command today.
   - A tap runs it the way a gesture runs its command: as if you had typed it and pressed Enter
     (=onGesture= hands it to =processor.run=). It may be =torch= or =dnd=, because you chose it.
   - This is /not/ the path of a tapped history line. That path needs =launch.instant all= and
     refuses sensitive commands, so half the buttons would do nothing.
   - A script can't write to this list.

What is refused, and why:

- *A command in a description* (~{ command = "…" }~). It would break the rule that a script can't
  plant a one-tap command. A timer run could store it, and a later tap would run it unseen. Path 1
  gives a script the same reach, with the checks that exist.
- *Toggling the torch, the volume or media from a script.* Those commands are sensitive, and
  scripts have no function for them. They belong in Shortcuts (path 3) or in the Now playing
  widget.

*** Toggles

A =toggles= widget shows switches. Each has =on= (true or false) and a =tap= with =args=.

1. You tap. The switch shows "working".
2. The script runs with the arguments. It changes the thing (=device.setDnd(…)=) and calls
   =widget.show= with the new state.
3. The switch takes the new state. If no new state comes in 10 seconds, it goes back and the card
   says the run failed.

Kolahal never guesses the new state. The script reports it.

*** The card's own menu

A long-press on a script widget opens a menu that Kolahal owns. A script can't change it:

- Refresh
- Run in the log (for a command script)
- Options (opens the script's sheet)
- Edit script
- Resize and move (opens the Widgets screen with this widget selected)
- Remove

On the Widgets screen in edit mode, a tap selects a widget and does not reach it. This is how app
widgets behave there today.

** 5. Layout and look

*** Sizes

The page has 12 columns. Script widgets name their size in /cells/ of a 4-column grid, as people
know from home screens. One cell is 3 columns.

| Size | Columns | Height                 | Good for                         |
|------+---------+------------------------+----------------------------------|
| 1×1  |       3 | 1 row                  | one number, one ring, one button |
| 2×1  |       6 | 1 row                  | a number with its label          |
| 2×2  |       6 | 2 rows                 | a small list, a ring, a chart    |
| 4×1  |      12 | 1 row                  | a row of numbers or buttons      |
| 4×2  |      12 | 2 rows                 | a list, a chart, an agenda       |
| 4×4  |      12 | 4 rows                 | a long list, a picture           |

- One row is as tall as one cell is wide on this phone, and at least 88 dp. So 1×1 is about square.
  On a page 360 dp wide a cell is 80 dp; =WidgetLayout.widthDp(page, 3)= gives it.
- =h= rows are =h= × row + (=h= − 1) × 8 dp, to match the 8 dp gap between widgets.
- The size is only where a widget /starts/. After that it is a placed widget like any other: the
  toolbar changes its width in twelfths and its height in 8 dp steps, and Square still works. For
  script widgets the toolbar adds the six sizes as one-tap buttons.
- A script widget is at least 3 columns wide and 72 dp tall.
- The card draws for the box it gets, not for the size it asked for. Each kind has three layouts:
  small, wide and large, chosen from the measured width and height. Each kind says what it leaves
  out when it is small (the catalog lists it). What is left out is still read by a screen reader.

*** One page, one list

- Script widgets, built-in widgets and app widgets share one ordered list and one =WidgetFlow=.
  You can put the weather card beside another app's clock.
- =PlacedWidget= gets a =source= field for the new widgets. Such an entry has no AppWidget id, and
  it is not "pending". In the stored line, the provider field holds the source:

  | Source          | What it is                                   |
  |-----------------+----------------------------------------------|
  | =script:<name>= | the widget a script fills with =widget.show= |
  | =status:<name>= | the Status card of a script's status line    |
  | =builtin:<id>=  | a built-in widget, such as =builtin:battery= |

- Script names are =a-z=, =0-9=, =-= and =_= only ([[src:script/ScriptNames.kt::val NAME][ScriptNames.NAME]]), so the line's
  separators can't appear. The codec still refuses a source with =|= or a line break, as it
  refuses such a provider from a backup today.
- An older Kolahal skips a line whose provider has no =/=. So going back to an older version
  drops these widgets and breaks nothing.
- One script can have both cards placed: its own widget and its Status card. They are two entries.
  Weather, for example, will have a =@widget= line and still call =status()=.
- A widget is placed once. The picker shows a placed one as "Added".

*** Placed, and the =widget= access item

- The placed list is the source of truth. It is in the main process's preferences, which the
  =:script= process can't follow.
- So the main process copies "placed" into the script's access, as the item =widget=. Both
  processes read that from the database, and =widget.show= uses it to decide whether to store.
- When the two disagree, *the placed list wins*. At start and after a backup is imported, the main
  process sets =widget= on for each placed =script:<name>= entry and off for every other script.
  This matters after a restore: a backup carries only the access you switched /off/, so without
  this step a restored widget would stay empty for ever.
- The item covers only =widget.show=. A Status card needs no item: a status line is stored whether
  or not anything shows it, as today. Being placed is all a Status card needs.
- A rename moves everything with the script, as it moves the status line today
  ([[src:data/ScriptRepository.kt::fun rename][ScriptRepository.rename]]): the state, and the placed =script:= and =status:= entries.

*** The picker

The widget picker gets a first section, *Kolahal*, above the apps:

1. Built-in widgets.
2. Your scripts that have a =@widget= line, and scripts with a status line (as a Status card).
3. Library scripts with a widget that you haven't added. Each entry says what the script uses
   (the internet, a key). Picking one adds the script, as =script install= does, and places the
   widget.

Each entry shows a drawn sample of its kind and its sizes. =widget add <script>= and
=widget rm <script>= do the same from the prompt. =widget= is a sensitive command, so a script
can't run it.

*** Theme

- The cards are drawn inside =GuiTheme=, so they use the Material scheme that =schemeFrom= builds
  from the terminal palette. They change with =theme=, in the dark and the light version.
- The page behind is the terminal's colour, or the wallpaper (=widgets.wallpaper=). So each card
  has its own opaque surface: =surfaceContainerHigh=. Text keeps its contrast over any wallpaper.
- A =color= role maps to the palette with [[src:ui/LogLineText.kt::internal fun colourOf][colourOf]], which the log uses for =fmt.color=.
- Text uses the GUI's typeface, as Settings and Scripts do. See [[*Open questions][Open questions]].

*** Accessibility

- Each card is one item for a screen reader: "Weather, Pune: 24 degrees, Sunny. Updated 5 minutes
  ago." Items with their own tap are separate items inside it.
- Every tap target is at least 48 dp. A kind shows fewer buttons in a small box and never smaller
  ones.
- A chart has words. The script can give =summary=. Without one, Kolahal says "7 values, from 3 to
  12, the latest 9".
- A picture needs =alt= text.
- Colour is never the only sign. An error has words and an icon. A toggle has a shape and a state.
- Text follows the system font size. Long text is cut with "…".
- Rows run right to left in a right-to-left language. =WidgetFlow= does this already.
- Custom actions for a screen reader: Refresh, Resize and move, Remove.
- Content that changes by itself is not announced each time. That would be noise.

** 6. Safety and privacy

*** What a script can and can't do with a widget

- It can fill a card of a fixed kind. It can't draw, place views, or run code in the main process.
- It can't place, move, resize or remove a widget. The =widget= access item is on only while you
  have placed it, as =header= is on only while you pinned the script.
- It can't put a command behind a tap ([[*4. Interaction][Interaction]]).
- It can't make the card say "Kolahal" things. The footer and the state messages are Kolahal's.

*** Every text and link is checked

- Every text is passed through =redact= first. A secret's value, and its stand-in mark, never reach
  the screen or the database.
- A link (=url=) and a picture (=image=) pass =safeWebUrl=: =http= and =https= only, the internet
  switch on, and no secret sent to a site its =@secret= line doesn't name. A link that fails stops
  the run with an error that says why, as a refused request does. A card with a dead tap would be
  worse.
- Home fetches a picture when the card shows. This is what a log line's =image= does today, and it
  uses that cache.

*** What a widget may show on home

| Data                  | Rule                                                                                                          |
|-----------------------+---------------------------------------------------------------------------------------------------------------|
| Secrets               | Never. They are masked before anything is stored.                                                             |
| Notifications         | Only from a script with =@uses notifications= allowed. The log shows notifications today, so this is no new exposure. No ready-made widget does it. |
| The clipboard         | Not useful: Android lets only the app in front read it, so a timer run gets nothing. No widget for it.        |
| The private space     | Never. Scripts can't see its apps or its notifications today, and an =app= tap never opens one.                |
| Your app list         | Only with =@uses apps= allowed.                                                                               |
| Todos, notes, calendar | Built-in widgets only, in phase 2. Scripts get read functions in phase 3, each behind a new =@uses= item.    |

*** When the private space is locked

- An app widget from the private space shows "private space locked", as today.
- A script widget holds nothing from the private space, so locking changes nothing for it.
- Built-in widgets never read the private space.

*** Who sees the widgets page

- Kolahal draws nothing on the lock screen. The page shows only after unlock.
- The page can appear in the Recents picture of home, as the log can today.

*** Limits that stop a runaway script

- At most 20 =widget.show= calls in a run. The same description again is skipped.
- At most 32 KB for a description.
- =refresh= no faster than every 10 seconds, and only while the widget is in view.
- A tap on one item starts at most one run in 2 seconds.
- All run limits stay: 60 seconds, 64 MB, the watchdog.

*** What a backup holds

- A backup holds where each widget is, not what it shows.
- The state scopes join =Stores.THIS_PHONE=. So they don't go into a backup file, a restore keeps
  this phone's, and a new phone starts them empty.
- An imported script arrives switched off, as today. Its card says so and offers Turn on.

** 7. Performance and battery

- *No main-thread work.* Scripts run in =:script=. The main process reads state on an IO thread,
  only when the counter moves, and decodes only a description whose JSON text changed.
- *The page draws at once.* On a cold start the cards come from stored state. No script has to run
  first.
- *Cheap redraws.* The checked description is an =@Immutable= class. Cards have stable keys. A card
  redraws only when its own state changes.
- *Tickers.* One shared ticker, by the minute, like the header's =rememberNow=. A ticker by the
  second runs only for a clock or countdown that shows seconds. Both stop when the widgets page is
  not the page in view.
- *Bounded runs.*
  - =@every=: 15 minutes at the fastest. This is WorkManager's floor.
  - =refresh=: 10 seconds at the fastest, only in view, never two at once for one script.
  - Showing the page runs only widgets older than their =staleAfter=.
  - Two runs of one script never overlap. =ScriptRun= holds a lock for each script.
- *Caching.* Scripts use =http.cached=, as today. Pictures use the log's picture cache (50 MB at
  most), sized to the card.
- *Nothing new in the background.* When home is not on screen, only a script's own timers and
  events run, as today.
- *Memory.* The main process holds state for placed widgets only, each at most 32 KB.
- *Tap speed.* A tap with =args= takes as long as a button under a log line: WorkManager starts the
  run in =:script=. The tapped item shows "working" at once. Shortcuts and built-in widgets react
  in the main process, with no run.

** Backups

- *Placement travels.* The backup's ="widgets"= list gets an entry for each new widget: its
  source (=script:weather=, =status:cricket=, =builtin:battery=), a built-in's settings, the
  height, the order and the width.
- *They come back by themselves.* App widgets need "Add again", because their ids belong to one
  phone. A script widget needs only its script. =Backup.import= reads scripts before widgets, so
  the script is there. An entry whose script is missing is skipped and named.
- *The script arrives off*, as every imported script does. Its card says so.
- *The placed list wins.* A backup carries only the access you switched off. So after the import,
  the =widget= item is set on for each restored script widget.
- *State does not travel.* It is a cache and may hold private text. Options and script stores
  travel as today. Secrets never do.
- *Older versions are safe.* They read only entries with a provider that has a =/=. They skip the
  new ones. The backup's format number does not change.
- *Shortcuts' commands* are listed for review after an import.

* Open questions

Each has a recommended answer. The plan above assumes those answers.

1. *Where do widgets show in the first build?*
   Recommended: only on Kolahal's widgets page. Other launchers' home screens wait for phase 4.

2. *May a script put a terminal command behind a tap?*
   Recommended: no. A tap runs the same script again, and that run may use =launcher.run= under
   today's rules. Commands you pick yourself go in the built-in Shortcuts widget.

3. *Kolahal's own data (todos, agenda, now playing, battery): built-in widgets, or new script
   functions?*
   Recommended: built-in widgets first. They are live, need no new access items, and can do what
   scripts may not (mark a todo done, control media). Script functions come in phase 3.

4. *One widget for each script, or several?*
   Recommended: one in the first build. It is keyed by script name, as a status line is. Two
   cities then need two scripts. Several widgets from one script, each with its own options, is
   phase 3. The stored key leaves room for it.

5. *Should Shortcuts be in the first build?*
   Recommended: phase 2. It needs its own small editor. It does not depend on scripts, so it can
   move to the first build if it is the widget you want most.

6. *Which typeface do the cards use?*
   Recommended: the GUI's, as Settings and Scripts use. A setting for the terminal font can come
   later. The log stays the terminal; the cards are GUI.

7. *How does old content look?*
   Recommended: the same, with its age in a footer ("2 h ago"). Dimming would lower contrast.

8. *Do a refresh run's own =log()= lines reach the log?*
   Recommended: yes, the rule a pinned line's refresh has. Library scripts skip them when
   =event.name= is ="widget"=. One rule is easier to explain than two.

9. *How fast may =refresh= be?*
   Recommended: 10 seconds, as for a status line, and only while the widget is in view.

10. *Does a widget's content go into backups?*
    Recommended: no. Where it is placed does. The content is a cache and may hold private text.

11. *May a widget show notification text?*
    Recommended: yes, for a script with =@uses notifications= allowed, since the log already
    shows notifications. No ready-made widget does it.

12. *Does picking a library widget add and switch on its script in one step?*
    Recommended: yes. =script install= already adds a library script switched on, with what it
    declares allowed. The picker's entry says what the script uses before you pick it.

13. *What do users call them?*
    Recommended: just "widgets". The picker's sections say where each comes from: Kolahal, your
    scripts, the library, an app. "Script widget" and "built-in widget" are words for this
    document and the code.
