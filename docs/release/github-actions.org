#+TITLE: Building and releasing on GitHub Actions
#+STARTUP: showall

GitHub builds every push and publishes every release, so a release no longer depends on this
computer. Three workflows live in =.github/workflows/=.

| Workflow      | Runs on                                          | Does                                                                                  |
|---------------+--------------------------------------------------+---------------------------------------------------------------------------------------|
| =build.yml=   | every push and pull request that changes the app | the unit tests, both builds, the Play check; keeps the builds for 14 days            |
| =release.yml= | a pushed tag =v*=, such as =v0.3.1=              | the same, signed, then publishes the GitHub release and keeps the Play bundle 90 days |
| =site.yml=    | a push to =master= that touches =site/=          | builds the website and publishes it to GitHub Pages; not on forks                     |

Builds use Temurin JDK 25 (the same version as Android Studio's JDK here) and the Gradle wrapper,
and install the NDK version =app/build.gradle.kts= pins (=ndkVersion=): it strips the native
libraries (Lua, QuickJS) and puts their symbols in the Play bundle. The actions are on Node 24
majors; =gradle/actions/setup-gradle= stays on v5, as v6 puts its caching under Gradle's terms of
use instead of the MIT licence.

* What =build.yml= is for

A check that the code still builds and its unit tests pass, on a clean machine. It has no keys:
its APK is signed with the runner's own debug key and its bundle is unsigned, so they are for
looking at (the run's *Artifacts*), not for installing over a release.

It builds each commit once. Its first job, =once=, looks at the other runs of the same commit and
skips the build when there is a Release run, or another Build that is running or passed: a
version branch and then master often get the same commit, and a release builds it anyway. A
failed or cancelled run doesn't count. Pull requests and manual runs (=workflow_dispatch=) always
build.

* What a release run does

=release.yml=, step by step:

1. *Checks the tag, the version and the notes*: the tag must be =v= + =versionName= from
   =app/build.gradle.kts=, and =docs/release/notes/X.Y.Z.md= must exist.
2. *Signing keys*: decodes the two keystores from the secrets into the runner's temporary folder.
   No secrets, no release: it stops and says to run =tools/make-keys.sh --secrets=.
3. *Unit tests and signed builds*: =testDebugUnitTest=, =assembleRelease=, =bundlePlay=,
   then =assemblePlay -PplayApk= in a second run (the Play build as an APK, signed with the release
   key).
4. *The Play check*: =tools/check-play-build.sh= on the Play APK (see [[file:google-play.org][google-play.org]]).
5. *Checks the signatures*: both APKs must be signed, with the release key when the
   =RELEASE_CERT_SHA256= variable is set ([[file:signing.org][signing.org]]); the bundle must be signed, and not with
   a debug key. The run's summary lists each file's certificate.
6. *Packages*: =kolahal-X.Y.Z.apk=, =kolahal-X.Y.Z-play.apk=, =kolahal-X.Y.Z-mapping.zip= (R8's names for both builds, for
   reading crash traces with =retrace=) and the notes, with a last line naming the commit both
   APKs and the bundle are built from.
7. *Publishes the GitHub release* with both APKs and the mapping zip, marked as the latest.
8. *Posts to Discord*, when the =DISCORD_RELEASES_WEBHOOK= secret is set: a message in the
   server's =#releases= channel with the version, the Play notes (=X.Y.Z-play.txt=, when there is
   one), and links to the APK and the release. A failed post doesn't stop the run.
9. *Keeps the Play bundle* and its =mapping.txt= with the run, for 90 days.
10. *Uploads to Google Play*, when =PLAY_WIF_PROVIDER= and =PLAY_SERVICE_ACCOUNT= are set: the
    bundle on the testing track: a draft to roll out in Play Console, or sent for review with
    =PLAY_SEND_FOR_REVIEW= =true= ([[file:google-play.org][google-play.org]] → Uploads from the workflow). With them set, step 1 also wants =docs/release/notes/X.Y.Z-play.txt=.

* Who can release

Only the repository's owner.

- A ruleset, /Only the owner makes tags/ (Settings → Rules → Rulesets), stops anyone else creating,
  moving or deleting a tag, however they try: a push, or a new release on GitHub. Repository admin
  is the one role that bypasses it.
- The signing keys are secrets of the =release= environment (Settings → Environments), which only a
  run on a =v*= tag can use. A workflow pushed on a branch can't read them.
- Google lets only =release.yml= on a =v*= tag upload to Play ([[file:google-play.org][google-play.org]] → Uploads from the
  workflow).

* Secrets and variables

The secrets are in Settings → Environments → =release=. The variables are the repository's: Settings
→ Secrets and variables → Actions.

| Name                       | Kind     | Holds                                                |
|----------------------------+----------+------------------------------------------------------|
| =RELEASE_KEYSTORE_BASE64=  | secret   | =kolahal-release.jks=, as base64                     |
| =RELEASE_STORE_PASSWORD=   | secret   | its password                                         |
| =RELEASE_KEY_ALIAS=        | secret   | =kolahal=                                            |
| =RELEASE_KEY_PASSWORD=     | secret   | the key's password (the same one)                    |
| =UPLOAD_KEYSTORE_BASE64=   | secret   | =kolahal-upload.jks=, as base64                      |
| =UPLOAD_STORE_PASSWORD=    | secret   | its password                                         |
| =UPLOAD_KEY_ALIAS=         | secret   | =upload=                                             |
| =UPLOAD_KEY_PASSWORD=      | secret   | the key's password                                   |
| =DISCORD_RELEASES_WEBHOOK= | secret   | the =#releases= webhook's URL; optional              |
| =RELEASE_CERT_SHA256=      | variable | the release key's fingerprint; optional, recommended |
| =PLAY_WIF_PROVIDER=        | variable | the Google workload identity provider, for Play      |
| =PLAY_SERVICE_ACCOUNT=     | variable | the service account Play Console lets release        |
| =PLAY_TRACK=               | variable | the Play track, when it isn't =alpha=; optional      |
| =PLAY_SEND_FOR_REVIEW=     | variable | =true=: sent for review, not a draft; optional       |

=tools/make-keys.sh --secrets= sets the eight secrets from =keystore.properties=; run it again
after changing a key. Secrets can be replaced but never read back.

* Cutting a release

#+begin_src sh
git tag -s vX.Y.Z -m "Version X.Y.Z"   # on the version commit, with docs/release/notes/X.Y.Z.md
# One push for the branch, master and the tag, so Build sees the Release run and skips.
git push --atomic origin X.Y.Z X.Y.Z:master vX.Y.Z
gh run watch                           # pick the Release run
gh run download <run id> -n kolahal-X.Y.Z-play    # the Play bundle and its mapping.txt
#+end_src

* When a run fails

- *The tag doesn't match =versionName=*: delete the tag here and on GitHub, fix, tag again.
  #+begin_src sh
  git push --delete origin vX.Y.Z && git tag -d vX.Y.Z
  #+end_src
- *The notes are missing*: add =docs/release/notes/X.Y.Z.md=, commit, push, and tag again as above.
- *The keys aren't set up*: =tools/make-keys.sh --secrets=.
- *An APK is signed with another key*: a secret holds the wrong keystore. Store the right one
  again; never change =RELEASE_CERT_SHA256= to fit a wrong key.
- *The Play check fails*: something added a restricted permission or service to the Play build,
  often a new library. =aapt2 dump permissions= on the APK shows it; remove it in
  =app/src/play/AndroidManifest.xml= with =tools:node="remove"=, or drop the library.
- *A unit test fails*: the run's failed step shows it; =./gradlew :app:testDebugUnitTest= does the
  same here.
- A failed run publishes nothing, but the website already points its download button at the
  missing release, so fix it soon. Then move the tag to the fix: =git tag -d vX.Y.Z=,
  =git push origin :refs/tags/vX.Y.Z=, and tag and push again.

* Still done on this computer

These need an emulator or a phone, so they stay out of GitHub Actions:

- the on-device tests (=connectedDebugAndroidTest=, on the emulator only), and the coverage figure
  in README.org → Tests that comes from them;
- regenerating the startup (baseline) profile;
- installing the release on the maintainer's phone.

* The same builds here

#+begin_src sh
./gradlew :app:testDebugUnitTest :app:assembleRelease :app:bundlePlay
./gradlew -PplayApk :app:assemblePlay
tools/check-play-build.sh
#+end_src

With =keystore.properties= present they come out signed as on GitHub; outputs are under
=app/build/outputs/= (=apk/release/=, =apk/play/=, =bundle/play/=, =mapping/=).
