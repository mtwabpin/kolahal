#+TITLE: Releasing Kolahal
#+STARTUP: showall

How Kolahal is built, signed and published, and why it is set up this way. Start here; the
details are in the files beside this one. (This folder is for the maintainer; the website is in
=site/=.)

* The files here

- [[file:signing.org][signing.org]]: the keys. What each file in =~/.config/keys= is, why Kolahal has
  two where an app only on Play needs one, where they are used, and how to back them up.
- [[file:play-signing.org][play-signing.org]]: giving Play the release key, once, with PEPK and Android Studio's Java.
- [[file:github-actions.org][github-actions.org]]: the Build and Release workflows, their secrets, what a release
  run does, and what to do when one fails.
- [[file:google-play.org][google-play.org]]: Google Play: the Play build, the policy behind it, setting up Play
  Console, and each Play release.
- [[file:graphics/][graphics/]]: the store icon, feature graphic and screenshots, with the sources they are
  rendered from (=tools/play-graphics.sh=; google-play.org → Graphics).
- [[file:notes/][notes/]]: the release notes, one file per version (=notes/0.3.1.md=). The Release
  workflow publishes them as the GitHub release's notes.

* Two builds

One commit makes three files:

| Build | File                     | Gradle task                  | Signed with     | Goes to         |
|-------+--------------------------+------------------------------+-----------------+-----------------|
| Full  | =kolahal-X.Y.Z.apk=      | =assembleRelease=            | the release key | GitHub releases |
| Play  | =kolahal-X.Y.Z-play.apk= | =assemblePlay -PplayApk=     | the release key | GitHub releases |
| Play  | =kolahal-X.Y.Z-play.aab= | =bundlePlay=                 | the upload key  | Google Play     |

- *Full* is the app with everything: the screen lock (=lock=, double-tap), notifications in the
  log (=notifs=, media controls, scripts' notification triggers) and calls in the log (=calls=).
- *Play* leaves out the accessibility service, the call log, reading contacts and =update=: Google Play's
  policy doesn't let a launcher read the call log at all, wants a declaration, consent screens and a
  video for an accessibility service, wants the contact picker where it's enough, and lets an app
  update only through Play. Leaving the first two out was decided on 22 October 2026, for good on
  26 October.
  It has notification access since 0.4.6, asked for with an in-app disclosure first.
  [[file:google-play.org][google-play.org]] has the policy. The bundle is signed with the upload key, and Play turns it into
  APKs signed with the release key ([[file:signing.org][signing.org]]).
- The Play build's APK on GitHub is the same app as on Google Play. Since 0.4.6 it declares a
  notification listener too, so Play Protect can block it when sideloaded in India and some other
  countries, as it does the full build. =-PplayApk= signs it with the release key, like the full
  APK: one build type can't carry two keys, so the Release workflow builds it in a second Gradle
  run.
- All three install as the same app, signed with the same key on the phone, so any one installs
  over another, keeping the data. (Until 0.3.0 the GitHub APK without the three was called lite.)

How: =app/src/play/AndroidManifest.xml= removes the accessibility service, =READ_CALL_LOG= and
=READ_CONTACTS=; the =play= build type starts from =release= (=app/build.gradle.kts=). The
=BuildConfig= switches =LOCK_SERVICE= and =CALL_LOG= turn the features off: their commands aren't
suggested or listed in =help=, and typed anyway they say "This build has no …". =CONTACTS= switches
=call=, =sms= and =contacts= to Android's contact picker.
=tools/check-play-build.sh= checks the Play APK (=assemblePlay=, the bundle's manifest) and fails if
it ever asks for a restricted permission again.

* How a release travels

#+begin_example
version bump + notes/X.Y.Z.md ── commit, push master ── push tag vX.Y.Z
                                                            │
                                     Release workflow on GitHub Actions
                         (tests, builds, signs, checks, publishes)
                           │                                    │
     GitHub release: both APKs                      kolahal-X.Y.Z-play.aab, kept
     and the mapping zip                            with the run for 90 days
                           │                                    │
     the website's download button                  you upload it in Play Console
     points at it (site/src/release.ts)             (internal → closed → production)
#+end_example

* Making a release

1. Bump =versionCode= (by one) and =versionName= in =app/build.gradle.kts= (from =X.Y.Z-dev= to
   =X.Y.Z=), and =version= in =site/package.json=. The website's download button reads that
   version, so it points at the new APK as soon as the site deploys: tag right after pushing.
   Between releases =versionName= says the next version with =-dev= (=0.4.6-dev=), so builds from
   the branch say what they are; =site/package.json= keeps the released one until the release.
   Scripts' =@requires= compares the numbers only, so =0.4.6-dev= counts as 0.4.6.
2. Write =notes/X.Y.Z.md= (see [[file:notes/README.md][notes/README.md]]) and, for Play, =notes/X.Y.Z-play.txt=.
3. Test on the computer: the unit tests, the on-device tests on the emulator (never on a phone
   you use: they install a debug build and change its settings), the coverage figure in
   README.org → Tests, and =tools/check-play-build.sh= after =./gradlew :app:assemblePlay=.
4. Commit =Version X.Y.Z (versionCode N)= with the notes and the coverage figure, and push
   =master=.
5. =git tag vX.Y.Z && git push origin vX.Y.Z=, then watch the run: =gh run watch=. It publishes
   the GitHub release by itself.
6. Google Play: the run puts the bundle on the testing track, with =notes/X.Y.Z-play.txt= as its
   notes, sent for review (=PLAY_SEND_FOR_REVIEW=) or as a draft to roll out in Play Console.
   By hand, when the upload isn't set up or failed: download the bundle (=gh run download <run
   id> -n kolahal-X.Y.Z-play=), upload it in Play Console, and paste the notes.
7. Check the website deployed (the Website workflow) and its download button works.

* History

- 0.1.0 to 0.3.0 were built on the maintainer's computer and published by hand with =gh=. Their
  APKs are signed with that computer's debug key (=~/.android/debug.keystore=).
- 22 October 2026: the release and upload keys, the GitHub Actions workflows and the Play build.
- 22 October 2026, later: the lite build leaves the call log out too, and becomes the version on
  Google Play (before, lite still read the call log and Play had a build of its own).
- 22 October 2026, later still: no lite APK from 0.3.1 on. The Play build is the only one
  without the three, and starts from the release build.
- The first release signed with the release key can't install over the debug-signed ones: every
  install, the maintainer's phone included, moves once by Settings → Backup → Export everything,
  uninstall, install, import. Its notes must say so. [[file:signing.org][signing.org]] explains why.
