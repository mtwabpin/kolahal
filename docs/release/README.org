#+TITLE: Releasing Kolahal
#+STARTUP: showall

How Kolahal is built, signed and published, and why it is set up this way. Start here; the
details are in the files beside this one. (This folder is for the maintainer; the website is in
=site/=.)

* The files here

- [[file:signing.org][signing.org]]: the keys. What each file in =~/.config/keys= is, why Kolahal has
  two where an app only on Play needs one, where they are used, and how to back them up.
- [[file:play-signing.org][play-signing.org]]: giving Play the release key, once, with PEPK and Android Studio's Java.
- [[file:github-actions.org][github-actions.org]]: the Build and Release workflows, their secrets, what a release
  run does, and what to do when one fails.
- [[file:google-play.org][google-play.org]]: Google Play: the Play build, the policy behind it, setting up Play
  Console, and each Play release.
- [[file:video.org][video.org]]: the plan for the preview video on the Play listing (not recorded yet):
  Play's rules for it, the frame, the shot list with the exact commands and scripts, the data to
  prepare on the emulator, and how to record and put it together.
- [[file:graphics/][graphics/]]: the store icon, feature graphic and screenshots, with the sources they are
  rendered from (=tools/play-graphics.sh=; google-play.org → Graphics).
  =graphics/icon-ideas/= keeps four drawings for a later launcher icon, chosen
  by the maintainer on 24 November 2026 from two sets of ideas: A (today's icon with fewer, bolder
  parts), B (the log over a dusk scene), F (the log's lines rising into ridges) and G (today's icon
  in the website's colors). B is the website's icon since that day (=site/public/favicon.svg=,
  =site/src/assets/logo.svg=) and the picture at the top of the repository's README; the app's icon
  has not changed.
- [[file:notes/][notes/]]: the release notes, two files per version: =notes/0.3.1.md= for GitHub and
  =notes/0.3.1-play.txt=, the short notes for Google Play. The Release workflow publishes the first
  as the GitHub release's notes and sends the second to Play and to Discord.

* Two builds

One commit makes three files. The APKs aren't published until Kolahal is public on Google Play
(=PUBLISH_APKS= in =release.yml=, since 22 November 2026): the GitHub release has the notes and the
mapping zip, and people install from Play. They are still built and checked.

| Build | File                     | Gradle task              | Signed with     | Goes to                              |
|-------+--------------------------+--------------------------+-----------------+--------------------------------------|
| Full  | =kolahal-X.Y.Z.apk=      | =assembleRelease=        | the release key | GitHub releases, with =PUBLISH_APKS= |
| Play  | =kolahal-X.Y.Z-play.apk= | =assemblePlay -PplayApk= | the release key | GitHub releases, with =PUBLISH_APKS= |
| Play  | =kolahal-X.Y.Z-play.aab= | =bundlePlay=             | the upload key  | Google Play                          |

- *Full* is the app with everything: the screen lock (=lock=, double-tap), notifications in the
  log (=notifs=, media controls, scripts' notification triggers), calls in the log (=calls=),
  contacts read by name, and =update=.
- *Play* leaves out the accessibility service, the call log, reading contacts and =update=: Google Play's
  policy doesn't let a launcher read the call log at all, wants a declaration, consent screens and a
  video for an accessibility service, wants the contact picker where it's enough, and lets an app
  update only through Play. Leaving the first two out was decided on 22 October 2026, for good on
  26 October.
  It has notification access since 0.4.6, asked for with an in-app disclosure first.
  [[file:google-play.org][google-play.org]] has the policy. The bundle is signed with the upload key, and Play turns it into
  APKs signed with the release key ([[file:signing.org][signing.org]]).
- The Play build's APK on GitHub is the same app as on Google Play. Since 0.4.6 it declares a
  notification listener too, so Play Protect can block it when sideloaded in India and some other
  countries, as it does the full build. =-PplayApk= signs it with the release key, like the full
  APK: one build type can't carry two keys, so the Release workflow builds it in a second Gradle
  run.
- All three install as the same app, signed with the same key on the phone, so any one installs
  over another, keeping the data. (Until 0.3.0 the GitHub APK without the three was called lite.)

How: =app/src/play/AndroidManifest.xml= removes the accessibility service, =READ_CALL_LOG=,
=READ_CONTACTS=, =REQUEST_INSTALL_PACKAGES= and the updater's file provider and receiver; the =play=
build type starts from =release= (=app/build.gradle.kts=). The =BuildConfig= switches
=LOCK_SERVICE=, =CALL_LOG= and =SELF_UPDATE= turn the features off: their commands aren't suggested
or listed in =help=, and typed anyway they say why they're missing ("This build has no
accessibility service …", "This build updates through Google Play …"). With =SELF_UPDATE= off the
updater's code is never reached, so R8 removes it. =CONTACTS= switches =call=, =sms= and =contacts=
to Android's contact picker.
=SHADER_OVER_APPS= is off as well, and the manifest removes =SYSTEM_ALERT_WINDOW=: a one-off shader
plays over other apps in the full build only, so the Play build has no setting, no =allow overlay= and
no window for it.
=tools/check-play-build.sh= checks the Play APK (=assemblePlay=; it has the bundle's manifest) and
fails if it ever asks for a restricted permission again or carries the updater or that window.

* How a release travels

#+begin_example
version bump + notes/X.Y.Z.md ── commit, tag vX.Y.Z ── push branch, master and tag
                                                            │
                                     Release workflow on GitHub Actions
                         (tests, builds, signs, checks, publishes)
                           │                                    │
     GitHub release: the mapping zip, and           kolahal-X.Y.Z-play.aab, kept
     both APKs if PUBLISH_APKS is on                with the run for 90 days
                           │                                    │
     the website's APK buttons point at it          the run uploads it to Play's testing
     when DIRECT_DOWNLOADS_ON is on                 track (or you do, in Play Console);
     (site/src/release.ts)                          closed test → production
#+end_example

* Making a release

1. Bump =versionCode= (by one) and =versionName= in =app/build.gradle.kts= (from =X.Y.Z-dev= to
   =X.Y.Z=), and =version= in =site/package.json=. The website reads that version (its download
   buttons, when they are on, point at the new APK as soon as the site deploys): tag right after pushing.
   Between releases =versionName= says the next version with =-dev= (=0.4.6-dev=), so builds from
   the branch say what they are; =site/package.json= keeps the released one until the release.
   Scripts' =@requires= compares the numbers only, so =0.4.6-dev= counts as 0.4.6.
2. Write =notes/X.Y.Z.md= (see [[file:notes/README.md][notes/README.md]]) and, for Play, =notes/X.Y.Z-play.txt=.
3. Test on the computer: the unit tests, the on-device tests on the emulator (never on a phone
   you use: they install a debug build and change its settings; =tools/device-tests.sh= runs them
   on one or two emulators), the coverage figure in README.org → Tests (=./gradlew -Pcoverage
   :app:createDebugUnitTestCoverageReport :app:createDebugAndroidTestCoverageReport=, then
   =perl tools/coverage.pl=), and =tools/check-play-build.sh= after =./gradlew :app:assemblePlay=.
4. Commit =Version X.Y.Z (versionCode N)= with the notes and the coverage figure.
5. Tag it and push the branch, master and the tag together:
   =git tag -s vX.Y.Z -m "Version X.Y.Z"= and =git push --atomic origin X.Y.Z X.Y.Z:master vX.Y.Z=.
   One push lets the Build workflow see the Release run and skip the same build. Watch the run:
   =gh run watch=. It publishes the GitHub release by itself.
6. Google Play: when the upload is set up (=PLAY_WIF_PROVIDER=, =PLAY_SERVICE_ACCOUNT=), the run puts
   the bundle on the testing track, with =notes/X.Y.Z-play.txt= as its notes, sent for review
   (=PLAY_SEND_FOR_REVIEW=) or as a draft to roll out in Play Console.
   By hand, when the upload isn't set up or failed: download the bundle (=gh run download <run
   id> -n kolahal-X.Y.Z-play=), upload it in Play Console, and paste the notes.
7. Check the website deployed (the Website workflow) and its install button works.
8. The shared scripts (the =kolahal-scripts= repository): merge its =X.Y.Z= branch into =main= and push
   =main=. Kolahal X.Y.Z reads the site's =X.Y.Z/= folder, built from that branch; =main= is the root,
   which every Kolahal up to 0.5.16 reads, and which a newer one reads when a source has no folder
   for its version. The branch stays, for fixes to that version's scripts.

Between releases the library, the script header and the shader rules change with the app. The same
piece of work brings =kolahal-scripts= in line, on its branch named after the next Kolahal (made from
the last version's branch when the work starts), and =kolahal-scripts-template= where its check
changes. Both are pushed then, not at the release: the site publishes each version branch in a
folder of its own, so nothing reaches an older Kolahal.

* History

- 0.1.0 to 0.3.0 were built on the maintainer's computer and published by hand with =gh=. Their
  APKs are signed with that computer's debug key (=~/.android/debug.keystore=).
- 22 October 2026: the release and upload keys, the GitHub Actions workflows and the Play build.
- 22 October 2026, later: the lite build leaves the call log out too, and becomes the version on
  Google Play (before, lite still read the call log and Play had a build of its own).
- 22 October 2026, later still: no lite APK from 0.3.1 on. The Play build is the only one
  without the three, and starts from the release build.
- The first release signed with the release key can't install over the debug-signed ones: every
  install, the maintainer's phone included, moves once by Settings → Backup → Export everything,
  uninstall, install, import. Its notes must say so. [[file:signing.org][signing.org]] explains why.
