#+TITLE: Kolahal on Google Play
#+STARTUP: showall

Kolahal is in testing on Google Play: the first bundle (0.4.6-dev, versionCode 15, the Play build
with notification access) was approved in internal testing on 26 October 2026, and the Release
workflow has uploaded to the closed test since 0.4.8. It isn't in production yet. This is what is
ready, what Play's policy asked for, and the steps left. Each bundle needs a higher versionCode
than the last.

* Before production

Play needs a closed test before production: 12 or more testers opted in for 14 days in a row,
then Dashboard → Apply for production (review usually takes 7 days or less). Testers who opt out
before day 14 don't count.

* On Play: the Play build, and why it has less

Google Play gets the Play build, the full app without four things, packaged as a bundle:
=./gradlew :app:bundlePlay= (the Release workflow too). What it leaves out:

| Left out                                  | What goes with it                                  | Play's rule                                                                                                                                            |
|-------------------------------------------+----------------------------------------------------+--------------------------------------------------------------------------------------------------------------------------------------------------------|
| =READ_CALL_LOG=                           | calls in the log, =calls=                          | not allowed: Play's SMS and Call Log policy names "calls appearing in wallpaper, launcher, and other tools" as invalid, and launchers get no exception |
| the accessibility service (=LockService=) | double-tap to lock, =lock=                         | Play says launchers are not accessibility tools, so it would need a declaration, an in-app disclosure with consent, and a video of it                  |
| =REQUEST_INSTALL_PACKAGES=                | =update= and its code                              | Device and Network Abuse: an app updates only through Play                                                                                             |
| =READ_CONTACTS=                           | contacts read by name; the picker instead (below)  | Play's Contacts policy (apps targeting Android 17, from 27 January 2027): broad access only where Android's contact picker can't do the job, with a declaration |

The maintainer chose (26 October 2026) to leave the call log and the accessibility service out
for good rather than risk the declaration.

Neither build has =ACCESS_LOCAL_NETWORK=. The maintainer removed it (1 November 2026), with
=@uses lan= and =local-network=: from 25 August 2027, Play lets an app targeting Android 17 ask for
it only with a declaration, for core functionality a device picker can't serve. Kolahal doesn't check
where a request goes: on Android 17, Android blocks the local network itself.

Notification access is in (since 0.4.6): notifications in the log, =notifs=, media controls and
=@on notification= scripts. Play has no declaration form for a notification listener; its User
Data policy wants an in-app disclosure with consent before the access, so =notifs enable= (from the
prompt, Setup or the tour) shows what Kolahal reads, what for and that it stays on the phone, and
opens Android's Notification access screen only on *Allow* (=NotificationAccessDialog=). The Data
safety answer stays "no data collected": notifications never leave the phone. The Play-build APK on
GitHub has it too, so Play Protect can block it when sideloaded in India and some other countries,
like the full build.

Contacts are out since 0.4.7, by the same choice: no declaration. =call=, =sms= and =contacts= open
Android's contact picker (=ContactPicker=: Android 17's =ACTION_PICK_CONTACTS= session, before it
=ACTION_PICK= on phone numbers), which lets Kolahal read only the person picked. Kolahal keeps that
person's name and numbers on the phone (=picked_contacts= prefs, out of cloud backups) so the name
works by itself next time; =contacts --forget <name>= drops one. The Data safety answer stays "no
data collected": they never leave the phone.

Everything else stays, because Play doesn't restrict it or needs only a clear runtime request:
calendar, exact alarms (=SCHEDULE_EXACT_ALARM=, the one the user grants; the restricted
one is =USE_EXACT_ALARM=), usage access, system settings, Do Not Disturb, the private space, the
status bar, uninstall requests, and the app list (Kolahal uses =<queries>=, not the restricted
=QUERY_ALL_PACKAGES=). Scripts in Lua and JavaScript are allowed: Play forbids downloading
executable code (dex, JAR, .so), not interpreted code, as long as it can't be used to break Play's
policy.

Since 0.4.4 a script's daily time runs in a short foreground service (=ScriptRunService=, type
=shortService=, =FOREGROUND_SERVICE= only, no =FOREGROUND_SERVICE_*= type permission) for its few
seconds: Android lets a launcher pause or resume the work profile only in front, and the run
reaches the network while the phone dozes. If Play Console asks about it under App content →
Foreground service permissions: it runs a script the user installed, at a time the user set, for
seconds, started by an exact alarm the user allowed.

=tools/check-play-build.sh= checks the Play APK: it fails if any of these appear: the
call log, SMS or contacts permissions, =QUERY_ALL_PACKAGES=, =USE_EXACT_ALARM=, =REQUEST_INSTALL_PACKAGES=,
=MANAGE_EXTERNAL_STORAGE=, =ACCESS_BACKGROUND_LOCATION=, =ACCESS_LOCAL_NETWORK=, an accessibility service, or the self-updater (its address in the code, its file provider or its receiver). Both
workflows run it, so a library that adds one is caught.

Policy pages (opened 22 October 2026):
[[https://support.google.com/googleplay/android-developer/answer/9047303][SMS and Call Log]],
[[https://support.google.com/googleplay/android-developer/answer/10964491][AccessibilityService API]],
[[https://support.google.com/googleplay/android-developer/answer/16558241][sensitive permissions]],
[[https://support.google.com/googleplay/android-developer/answer/9888379][Device and Network Abuse]].

* The first time in Play Console

1. *Decide free or paid* first: a free app can never become paid later.
2. *Create the app*: name "Kolahal: Terminal Launcher", default language English, App.
3. *Play app signing*: give Play the release key, as in [[file:play-signing.org][play-signing.org]], before the first
   bundle goes up.
4. *App content*, the answers:
   | Form            | Answer                                                                                                                                                              |
   |-----------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
   | Privacy policy  | https://mtwabpin.github.io/kolahal/reference/privacy/ (it says what the Play build leaves out)                                                                      |
   | App access      | All functionality is available without special access (no login; a reviewer needs Kolahal as the home app to see it)                                                |
   | Ads             | No                                                                                                                                                                  |
   | Content rating  | All other app types; No to every content question; no user interaction; no unrestricted internet access (feeds open links in the browser)                           |
   | Target audience | 18 and over                                                                                                                                                         |
   | Data safety     | No data collected or shared: nothing is sent to the developer; feeds and searches go to the sites people chose; crash reports leave only as an email the user sends |
   | Category        | Personalization                                                                                                                                                     |
5. *Store listing*: paste the texts under [[*Store listing text][Store listing text]] below.
6. *Graphics*: upload the files in =graphics/=, as under [[*Graphics][Graphics]] below.
7. *Internal testing*: upload the bundle from a Release run; install it from the test link; read
   the pre-launch report.
8. *Closed testing*: 12 or more testers for 14 days in a row, then apply for production.

* Store listing text

Ready to paste into Play Console → Grow users → Store presence → Main store listing. It describes
the Play build: no screen lock and no calls in the log, so neither is mentioned. Play allows 4000 characters;
this is 3057. Keep it in step with the app when features change.

App name (30 characters at most; this is 26):

#+begin_example
Kolahal: Terminal Launcher
#+end_example

Short description (80 at most; this is 75):

#+begin_example
A keyboard-driven home screen that opens apps and runs commands as you type
#+end_example

Google flagged "A keyboard-first home screen: type part of an app's name and press Enter."
(22 October 2026), and its checks seem to match words: "keyboard-first" can read as "first", a
ranking claim, so the word "first" stays out of the store texts. Its [[https://support.google.com/googleplay/android-developer/answer/9866151#zippy=%2Cshort-description][short description rules]]: one sentence has no closing period
(periods only between sentences); no colons or other special characters, emoji or symbols, only
standard punctuation; no capitals for emphasis; no claims ("best", "new", "#1"), calls to action
("download now") or keyword lists; and no repeating the screenshots or feature graphic.

Full description:

#+begin_example
Kolahal turns your home screen into a terminal. Type part of an app's name and press Enter, or let the app open by itself once your letters can only mean one app. Everything else is a short command away.

TYPE, ENTER, DONE
• Type any part of an app's name: the closest match sits right above your thumb.
• Instant launch opens an app as soon as the letters match only that app.
• With an empty prompt, your most-used apps are one tap away; pin favourites to keep them at the front.
• Aliases for anything you type often, app shortcuts, and every past command one ↑ away.
• An app selector on an edge of the screen: slide your thumb along it to glide through all your apps, no keyboard needed.

A LOG YOU CAN ACT ON
• Every command and its output is a block with a coloured line beside it.
• Tap a line for its main action; long-press for copy, share, open, run again and more.
• Swipe a line right to copy it, left to delete it.
• App installs, updates and uninstalls show up as they happen.
• If you allow it, your notifications show up too, with media controls for what's playing.

LITTLE TOOLS BUILT IN
• A calculator with units and currencies: = 2^10, = 5 km in mi, = 100 usd in eur
• Web search with the engine you choose
• Call and text people by name: pick them once from your contacts
• To-dos, notes, reminders that survive a restart, timers and alarms through your clock app, and your calendar's agenda
• Screen time per app and an unlock counter
• Torch, volume, ring mode, Do Not Disturb, brightness, rotation and screen timeout from the prompt

FEEDS
• A built-in RSS and Atom reader with unread counts, refresh intervals, optional notifications, and OPML import and export.

SCRIPTS IN LUA OR JAVASCRIPT
• Run a script on a timer, at set times, or when something happens, such as unlocking the phone or plugging it in.
• Make a script into a command of your own that takes arguments.
• Pin a status line in the header, post a notification, fetch from the web.
• Start from 16 ready-made scripts (weather, Hacker News, a charge reminder and more) in an editor with completion.
• Scripts run sandboxed, in a separate process.

MAKE IT YOURS
• Seven colour themes, and a theme builder for your own, with a live preview

• A touch key bar, gestures that run any command, full screen, and a widgets page beside the terminal

PRIVATE BY DESIGN

WORK PROFILE AND PRIVATE SPACE

The screenshots are 1080 × 1920 (9:16, what Play recommends): a 1080 × 2400 phone capture fits
only inside a frame. The phones show the app in the vivid gruvbox theme, and the frames are gruvbox

=screenshot.html= (=SHOTS=); the font is the app's own JetBrains Mono.

** Taking the captures again

They must show the Play build: nothing about the screen lock or the call log.

1. On the emulator (never a phone you use), install the Play build:
   =./gradlew -PplayApk :app:assemblePlay= and =adb install -r app/build/outputs/apk/play/app-play.apk=.
   Locally it is signed with the release key, so an install with another key must be removed first
   (or re-sign a copy with the debug key to keep the emulator's data).
2. Settings as a new install has them, plus =config set header.network on= and
   =config set theme.name gruvbox=; a 1080 × 2400 screen (=adb shell wm size= shows it); the
   emulator in dark mode, so the keyboard is dark too (=adb shell cmd uimode night yes=).
   Three feeds (Hacker News, LWN, and NASA's Image of the Day:
   https://www.nasa.gov/feeds/iotd-feed/), three to-dos, and the =weather= script from the library
   on a 30-minute timer, with =script set weather city Pune=.
3. Each capture: =adb exec-out screencap -p > docs/release/graphics/raw/<name>.png=.
   | Capture     | What is on screen                                                                                          |
   |-------------+------------------------------------------------------------------------------------------------------------|
   | =1-home=    | after =clear=: =weather=, ~= 30 c in f~, ~= 5 km in mi~, ~= 100 usd in eur~, =todo=, =feed=; keyboard down |
   | =2-type=    | =ca= typed in the prompt, keyboard up; app icons on (the default)                                          |
   | =3-feeds=   | =feed read 5=, NASA: live news can carry headlines a store page shouldn't                                  |
   | =4-scripts= | =script edit weather=, keyboard hidden, scrolled to the top                                                |
   | =5-themes=  | Settings → Look & feel → Your themes → a theme, named =olive= (not saved)                                  |
4. =tools/play-graphics.sh=, then look at the results before uploading.

* Each release on Play

Once the upload from the workflow is set up (below), the Release run puts the bundle on Play on the
testing track, with =docs/release/notes/X.Y.Z-play.txt= as its notes. With =PLAY_SEND_FOR_REVIEW=
=true= it rolls it out at once, which sends it for Google's review, and testers get it once it's
approved (with managed publishing on, once it's also published: Play Console → Publishing
overview). Otherwise it's a draft: open Play Console → Test and release → the track, check it and
roll it out. The run's summary says which version code and track, and which of the two. Without it, or when the upload fails (the run fails at its last
step, after the GitHub release is out):

1. The Release workflow keeps =kolahal-X.Y.Z-play.aab= with its run:
   =gh run download <run id> -n kolahal-X.Y.Z-play=.
2. Play Console → the track → Create new release → upload the bundle, and the =mapping.txt= beside
   it if Play doesn't show readable crash traces on its own. From 0.4.6 the bundle carries the
   native libraries' symbols itself (=ndk.debugSymbolLevel=); 0.4.4 and 0.4.5 went without, and Play
   asks for a symbol file: a zip of the bundle's own =base/lib/<abi>/*.so= files, as =<abi>/*.so=,
   uploaded in the App bundle explorer, serves.
3. Paste =docs/release/notes/X.Y.Z-play.txt= (500 characters at most) as the release notes.
   The first ones on Play introduced Kolahal and how to start; later ones list what changed since
   the last one on Play.
4. Roll out.

* Uploads from the workflow

=tools/play-upload.sh= (the Release workflow's last step) uploads the bundle through the Google Play
Developer API: one edit with the bundle and the release on the track, committed together. The
bundle carries its R8 mapping and native symbols, so nothing else goes up. It costs nothing: the
API, the Google Cloud project and its service account are free, with no billing account.

There is no key to keep or leak. GitHub gives each run an identity token; Google's Workload
Identity Federation trusts it only from =release.yml= run by a =v…= tag in this repository
(checked by the repository's and its owner's numeric IDs, so a repository given the same name later
gets nothing), and swaps it for half an hour as a service account. Play Console lets that account
release Kolahal to testing tracks, and nothing else.

Set up once:

1. A Google Cloud project with the Google Play Android Developer API, the IAM Service Account
   Credentials API and the Security Token Service API on.
2. A service account in it, with no roles in Cloud and no key.
3. Play Console → Users and permissions → Invite new users: the service account's email, no
   account permissions, and for Kolahal only *Release apps to testing tracks* (and *View app
   information*).
4. A workload identity pool (=github=) with an OIDC provider for
   =https://token.actions.githubusercontent.com=, mapping =google.subject=assertion.sub=,
   =attribute.repository_id=assertion.repository_id= (and the repository, ref and workflow_ref), with
   the condition
   #+begin_example
   assertion.repository_id == '<repository id>' && assertion.repository_owner_id == '<owner id>'
     && assertion.ref.startsWith('refs/tags/v')
     && assertion.workflow_ref.startsWith('mtwabpin/kolahal/.github/workflows/release.yml@refs/tags/v')
   #+end_example
   (=gh api repos/mtwabpin/kolahal= gives both IDs).
5. On the service account, =roles/iam.workloadIdentityUser= for
   =principalSet://iam.googleapis.com/projects/<project number>/locations/global/workloadIdentityPools/github/attribute.repository_id/<repository id>=.
6. Repository variables (not secrets; they are only names): =PLAY_WIF_PROVIDER=, the provider's
   full name (=projects/<number>/locations/global/workloadIdentityPools/github/providers/<id>=), and
   =PLAY_SERVICE_ACCOUNT=, its email. =PLAY_TRACK= only when the track isn't =alpha=, Play's first
   closed testing track. =PLAY_SEND_FOR_REVIEW= =true= to send each release for review instead of
   leaving a draft. Without the first two the step doesn't run.

When it fails, the run's log has Google's answer: no track by that name (it lists the ones there
are), a version code Play already has, a permission Play Console hasn't given yet (it can take a
while after the invitation), or, sending for review, other changes waiting in Play Console (a
rejected update, say) that Play won't send on its own: upload that release by hand.
